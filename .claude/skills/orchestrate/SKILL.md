# Оркестрация

Оркестратор — основная сессия с этим скилом, отдельного агента нет. Исполнитель части — сессия
по скилу `change` или субагент `implementer`. Ревью — прежние субагенты.

## 1. Когда параллелить

Параллелить, только если все условия верны; иначе — подряд, по скилу `change`:

- частей две и больше, каждая — законченная правка со своим «Готово, когда»;
- множества файлов частей не пересекаются (§3);
- ни одной части не нужен результат другой: общий тип, новый вызов `platform`, поле состояния;
- часть не меньше ~100 строк правки: мельче — запуск исполнителя дороже самой работы.

Не больше трёх исполнителей одновременно: каждый читает инструкции и документы заново, а собирать
и ревьюить результат — одному контексту.

## 2. Разбор задачи

1. Выписать части. Для шагов плана — строка «Волны» фазы в `docs/roadmap.md` §3.
2. Каждой части — бриф по `docs/templates/task-brief.md`; в «Компоненты» — точный список файлов и
   каталогов, которыми часть владеет. Чего нет в списке, исполнитель не трогает.
3. Найти общее: типы, интерфейсы, вызовы `platform`, поля `store.State`, схемы `contract`. Общее
   делается **до** волны одной правкой («контракт сначала») и сливается раньше, чем стартуют части.
4. Разложить по волнам: внутри волны части независимы, между волнами — порядок зависимостей.
   Показать владельцу таблицу «часть · файлы · зависит от · исполнитель» и начать.

## 3. Общие файлы — у них один хозяин

| Файлы | Кто правит |
|---|---|
| `internal/platform/` (порт, обе реализации), `internal/store/state.go`, `internal/contract/` | правка «контракт сначала», до волны |
| `cmd/xm/`, `internal/app/`, таблица команд `internal/cli/` | сборочная часть, после волны |
| `docs/roadmap.md`, `docs/architecture/repository.md`, `docs/testing.md` §8, `docs/dev/dependencies.md`, `docs/compatibility.md`, `AGENTS.md`, `.claude/` | оркестратор при сборке; исполнитель возвращает готовые строки в отчёте |
| раздел своего пакета в `docs/architecture/components.md`, свой пакет и его тесты | исполнитель части |

## 4. Два способа

| Способ | Когда | Как |
|---|---|---|
| Параллельные сессии | шаги одной волны плана; владелец запускает сессии сам | каждая сессия — обычный `change`, своя ветка и свой черновик PR; общие документы правит та, что сливается последней, остальные дают строки в ответе |
| Исполнители одной сессии | одна задача из нескольких независимых частей | субагент `implementer` на часть, каждый в своём рабочем дереве (изоляция `worktree`), запуск одним сообщением; оркестратор собирает ветки в свою и делает один черновик PR |

Исполнителю передаётся только бриф и список его файлов: историю разговора и чужие части он не
получает. Факты об upstream выясняются до волны (`upstream-researcher`), а не каждым исполнителем.

## 5. Сборка и приёмка

1. Принять отчёты: у каждой части — выполненные условия брифа и итог `bash scripts/check.sh` в её
   дереве. Часть вышла за свои файлы — вернуть исполнителю, не чинить за него.
2. Слить ветки частей по очереди; конфликт в файле означает ошибку разбора в §2 — разобрать,
   а не выбирать сторону наугад.
3. Внести строки общих документов (§3); связать части в сборочной правке, если она есть.
4. `bash scripts/check.sh` на собранном дереве; затем ревью по `docs/dev/code-review.md` §1 —
   один раз на собранное изменение, а не на каждую часть.
5. Сверить каждое «Готово, когда»; отчёт владельцу — по форме `AGENTS.md`, по строке на часть.

## Ловушки

- Хук `publish-guard` проверяет каталог проекта, а не рабочее дерево исполнителя (задача A6 в
  `docs/roadmap.md` §7): исполнитель сам запускает `check.sh` в своём дереве до коммита.
- Два исполнителя добавляют по вызову в `platform` — это пересечение, даже если методы разные.
- «Заодно поправил общий документ» в части — причина конфликта при сборке.
- Провал одной части не откладывает остальные, но сборка ждёт всех, от кого зависит.
