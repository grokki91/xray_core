# ADR-0041: Правило UFW ставит транзакция установки, метка — в состоянии

- Статус: Принято (владелец, 2026-11-24; шаг 5 фазы 4)
- Уточняет: [ADR-0036](0036-install-changes-only-own.md)
- Дата: 2026-11-24

## Контекст

ADR-0036 разрешил единственное изменение фаервола при установке — правило UFW для порта Xray,
если UFW активен, и оставил открытым, кто его ставит, снимает и откатывает. Правило сети
(`.claude/rules/network.md`) требует назвать это в ADR, потому что ошибка в фаерволе отрезает
владельца от сервера (приоритет 1).

## Решение

- **Кто меняет.** `network` — единственное исключение из «`network` только читает»:
  `AllowPort(port)` выполняет `ufw allow <порт>/tcp`, `RevokePort(port)` — `ufw delete allow
  <порт>/tcp`. Других изменений система через `network` не получает. Вызывает их только
  `app` внутри транзакции.
- **Когда ставится.** Факты `network.Facts` дали `Firewall.CanAllow`: UFW активен, порт закрыт
  только политикой входящих по умолчанию, правила для порта нет. Правило уже есть, UFW выключен,
  явное правило `deny`, ограничение источника или иной фаервол — правило не ставится; для
  iptables и nftables — факт и команда в итоге (ADR-0036).
- **Метка.** `state.firewall.ufw_rule` — правило поставил `xm` (схема состояния 3, миграция 2 → 3
  с `false`). Снимает правило только `xm` и только по метке: чужое правило с тем же портом не
  трогается.
- **Откат.** Порт, для которого транзакция собирается добавить правило, записывается в журнал
  транзакции (`ufw_port`) до первого изменения. Откат — в том числе после сбоя до самого
  добавления и после убитого процесса — снимает правило безусловно: оно до транзакции
  отсутствовало (иначе его бы не добавляли). Снятие несуществующего правила UFW завершает с
  кодом 0, поэтому откат повторим. Отказ `ufw` при добавлении — провал транзакции и откат; отказ
  при снятии — `ErrRollbackFailed` (код 5).
- **Проверка SSH.** Правило «allow» не может закрыть уже открытый порт, поэтому доступ по SSH
  не уменьшается. После изменения контроль транзакции — набор `control` с самопроверкой;
  отдельной проверки порта SSH нет: `xm` его не трогает и не знает его номера. Это осознанное
  отступление от `.claude/rules/network.md`, оправданное тем, что правило только открывает порт.
  Правила, которые закрывают порты, `xm` не добавляет никогда.
- **Удаление.** `xm uninstall` (шаг 6) снимает правило, если метка стоит, и до этого не меняет
  фаервол.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Метка — комментарий в правиле UFW (`comment xm`) | зависит от формата вывода `ufw status`, владелец может переименовать комментарий; «чьё правило» должно быть однозначным |
| Только факт и команда, правило не ставить | установка перестаёт быть «одной командой» на хостерах с UFW; ADR-0036 уже допустил правило |
| Отдельный менеджер `firewall` | ради двух вызовов — новый пакет и граница; изменение живёт рядом с чтением того же фаервола |

## Последствия

- Схема состояния 3; старые установки мигрируют с `ufw_rule: false` — их правил `xm` не снимает.
- `network` теперь вызывает `ufw` с изменяющими аргументами; закрытый список программ
  `platform` не меняется.
- Окно гонки: `CanAllow` вычисляется до загрузки релиза; если владелец за это время сам
  добавил такое же правило, откат неудавшейся установки его снимет. Риск принят: окно — минуты
  одной команды, а правило возвращается `ufw allow`.
- Правило открывает порт для любого источника (и IPv4, и IPv6, если IPv6 включён в UFW):
  сужение источника — за владельцем.
- Пересмотреть, если появится `xm harden`: он станет владельцем всех правил фаервола.
