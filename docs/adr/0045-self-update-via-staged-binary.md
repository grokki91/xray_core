# ADR-0045: `xm update --self` — новый бинарник применяет себя сам

- Статус: Принято
- Дата: 2026-11-27
- Уточняет: [ADR-0013](0013-distribution-and-bootstrap.md), [ADR-0005](0005-transactions-and-rollback.md)

## Контекст

`updates.md` §8 требует обновлять `xm` из релиза этого репозитория той же проверкой, что у
загрузчика, с миграцией состояния и перерисовкой конфигурации новым `xm` внутри транзакции и
откатом при провале. Запущенный старый `xm` код новой версии выполнить не может. Не было решено:
кто ведёт транзакцию, как сообщается итог, где лежит прежний бинарник, чем проверяется загрузка.
Выбор владельца — 2026-11-27.

## Решение

- **Источник и проверка** — как у `install.sh`: последний стабильный релиз
  `grokki91/xray_core` через API (`update.NewSelf`), файлы `xm-linux-amd64` и `SHA256SUMS` того же
  релиза; SHA-256 файла сверяется с `SHA256SUMS`. Подписи и attestation нет — как у загрузчика.
- **Старый `xm`** (`xm update --self`) только загружает и сверяет файл, кладёт его в
  `/usr/local/lib/xm/xm.next` (0755, root), запускает программой закрытого списка `xm-next`
  без оболочки `xm-next version --json` — версия должна совпасть с тегом — и затем
  `xm-next self-apply --previous <версия старого> --json`. Документ, который вернул новый `xm`,
  старый передаёт владельцу как есть, вместе с кодом выхода.
- **Новый `xm`** (`self-apply`, скрытая служебная команда, в справке её нет) под блокировкой:
  откат незавершённой транзакции; `/usr/local/bin/xm` → `/usr/local/bin/xm.previous`, файл
  `xm.next` → `/usr/local/bin/xm`; затем транзакция `Change{Reason: "self-update", XMReplaced: true}`: миграция
  состояния до своей схемы, отрисовка конфигурации своими правилами, `xray run -test`, перезапуск,
  контроль. Журнал транзакции помечает замену (`xm_replaced`): откат — в том числе
  после обрыва — возвращает `xm.previous` на место. Провал до журнала тоже возвращает файл.
- Замена файла — до журнала: старый `xm`, оказавшийся на месте после отката, журнала с новым
  полем не встречает; обрыв между заменой и журналом оставляет новый `xm` с прежними
  состоянием и конфигурацией — их он читает миграцией в памяти.
- **Состояние** (схема 4): раздел `xm{version, previous}`. `version` записывает каждая
  транзакция — версия `xm`, что её применила; `previous` — `self-apply`. Миграция 3 → 4 — пустые
  строки.
- **Вывод** — схема `update` 1.1: поле `component` (`xray` или `xm`). Для `xm` диапазона и
  удержания нет: `range` пуст, `in_range: true`, `held: false`.
- `--self` не сочетается с `--check`, `--to`, `--rollback` (код 2). Релиз не новее текущей
  версии — ничего не делается, код 0. Сборка без версии вида `N.N.N` считается старше любой.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Старый `xm` меняет файл и зовёт новый «доприменить» | транзакция делится между двумя версиями, откат — из двух частей |
| Только заменить файл, миграция при следующей команде | изменение без транзакции и контроля, против `updates.md` §8 |
| Новая схема `self-update` | второй документ с теми же полями; выбор владельца — расширить `update` |
| Проверка `gh attestation` | новая зависимость; загрузчик её не делает |

## Последствия

- Служебная команда `self-apply` — часть контракта между версиями `xm`: её аргументы меняются
  только с обратной совместимостью.
- `xm` версий без `--self` обновляется повторным `install.sh` один раз.
- Подлинность релиза держится на HTTPS до GitHub и `SHA256SUMS` того же релиза — та же цена, что у
  загрузчика.
