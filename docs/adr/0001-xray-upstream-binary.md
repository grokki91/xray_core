# ADR-0001: Xray-core — внешний upstream-бинарник

- Статус: Принято
- Дата: 2026-11-13

## Контекст

Проект управляет официальным Xray-core. Upstream выпускается часто, меняет значения по умолчанию
и правила протоколов; любая собственная копия его кода начинает отставать в день создания.

## Решение

- Xray-core используется только как официальный бинарник из релизов `XTLS/Xray-core`.
- Форка нет. Патчей нет. Линковки `xray-core` как библиотеки Go нет.
- Взаимодействие — через три границы: файл конфигурации, подкоманды бинарника
  (`run -test`, `version`, `api statsquery` и другие из закрытого списка) и службу systemd.
- Знание об upstream (поля конфигурации, версии, пороги) хранится данными и документом
  [compatibility.md](../compatibility.md), а не предположениями в коде.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Собственный форк | бремя слияний и ответственность за безопасность чужого кода без объективной необходимости |
| Линковка как библиотеки | версия Xray намертво связана с версией `xm`; обновить ядро без выпуска `xm` нельзя; бинарник растёт в разы |
| Управление через gRPC API Xray (HandlerService) | API без аутентификации: включённый, он даёт любому локальному процессу добавить пользователя |

## Последствия

- Обновление Xray не требует выпуска `xm`, пока версия в проверенном диапазоне.
- Добавление и удаление профиля перезапускает службу: соединения рвутся на секунду.
  Пересмотреть, если это станет заметно пользователям.
- Проверка конфигурации стоит запуска процесса; формат вывода подкоманд — внешняя зависимость,
  покрытая интеграционными тестами на границах диапазона версий.
- Форк допустим только новым ADR с доказательством, что задача не решается конфигурацией.
