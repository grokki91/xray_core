# ADR-0006: Один прикладной слой, версионируемый контракт, SSH как транспорт

- Статус: Принято
- Дата: 2026-11-13

## Контекст

Нужны CLI, Web UI и API сейчас; несколько VPS, внешние диагностические узлы, `xray_client` и
новые интерфейсы — позже. Если каждый интерфейс реализует логику сам, поведение разойдётся, а
каждое расширение потребует нового сетевого слушателя.

## Решение

- Вся логика — в сценариях пакета `app`. Интерфейсы (`cli`, `api`, `webui`, `bridge`) —
  адаптеры: разобрать ввод, проверить, вызвать сценарий, показать результат.
- Все машинные выводы — типы пакета `contract` в общем конверте
  `schema: {name, major, minor}`; правила версий — [interfaces.md](../architecture/interfaces.md) §2.
- Удалённое взаимодействие (управление несколькими VPS, сбор наблюдений, мост для
  `xray_client`) использует SSH как транспорт и тот же контракт: управляющая сторона запускает
  `xm … --json` на узле. Собственного сетевого протокола и открытых портов нет.
- Локальный HTTP API существует только для Web UI и слушает только петлю.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Сетевой API с токенами для удалённого управления | новый открытый порт и своя аутентификация там, где SSH уже есть и уже защищён |
| Постоянный агент на узле | противоречит [ADR-0003](0003-process-model.md) |
| Свой формат вывода у каждого интерфейса | три описания одного и того же, расхождение неизбежно |

## Последствия

- Новый интерфейс (TUI, бот) — новый адаптер без изменения сценариев.
- Управление несколькими VPS требует доступа по SSH с управляющей машины и не требует изменений
  на узлах.
- Контракт — публичный: его изменение — событие с версией и ADR; эталоны в тестах обязательны.
- Форма конверта совпадает с принятой в `xray_client`, что удешевляет будущий мост; сами
  контракты моста решаются отдельно (вопрос Q4).
