# ADR-0030: Проверки diag — в пакете diag, без подпакета checks

- Статус: Принято (владелец, 2026-11-18)
- Уточняет: [ADR-0024](0024-health-verdict-and-shared-checks.md) в части «реестр `diag/checks`»
- Дата: 2026-11-18

## Контекст

ADR-0024 и [repository.md](../architecture/repository.md) называют реестр проверок подпакетом
`diag/checks`. Проверка возвращает типы `diag` (`Observation`, `Finding`), а движок `diag`
собирает реестр из проверок — подпакет и пакет импортировали бы друг друга. Подпакет, который
собирает `cmd/xm` или `app`, нарушает правило «подпакет менеджера импортирует только его менеджер».

## Решение

- Проверки — файлы пакета `diag` по категориям: `control.go` — набор `control`; новые категории —
  новые файлы. Подпакета `checks` нет.
- Измерения проверка получает через интерфейсы потребителя, объявленные в `diag`; реализации
  подставляет `app` из менеджеров — менеджеры друг друга не импортируют.
- Граф импортов и тест `cmd/xm/boundaries_test.go` не меняются.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Типы в подпакете `diag/types`, который импортируют `diag` и `checks` | два подпакета одного менеджера импортируют друг друга — новое правило графа и тест ради одного каталога |
| `checks` собирает `cmd/xm` | противоречит правилу подпакетов и тянет в `cmd/xm` логику |

## Последствия

- Пакет `diag` растёт вместе с каталогом фазы 5; выделить подпакет можно, когда типы вынесены в
  отдельный пакет, — отдельным ADR.
- Строки о `diag/checks` в `repository.md` и `overview.md` заменены на «проверки пакета `diag`».
