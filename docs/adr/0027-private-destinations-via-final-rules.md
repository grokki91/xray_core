# ADR-0027: Запрет частных адресов назначения — `freedom.finalRules`

- Статус: Принято
- Уточняет: [ADR-0007](0007-web-ui-access.md) (способ запрета)
- Дата: 2026-11-17

## Контекст

[policy.md](../security/policy.md) §4 требует, чтобы клиент VPN не доставал службы самого
сервера (угроза T3). Фаза 2 сделала запрет правилом `ip` → `blackhole` в маршрутизации с
`domainStrategy: IPOnDemand`. Для домена Xray разрешает имя при выборе маршрута, а `freedom`
соединяется после своего разрешения: между ними ответ DNS может измениться
([compatibility.md](../compatibility.md) §2). Владелец выбрал вариант B вопроса Q12 2026-11-17.

## Решение

- Запрет — `settings.finalRules` у исходящего `freedom`: `action: block` для `0.0.0.0/8`,
  частных, петлевых и link-local сетей IPv4 и IPv6. Правило проверяет адрес, на который
  действительно идёт соединение.
- Правило маршрутизации `ip` → `blackhole` и `IPOnDemand` убираются в той же правке: один
  запрет — одна реализация.
- Переход и доказательство на трафике — задача A1 ([roadmap.md](../roadmap.md) §7): тест через
  петлю падает без правила. До A1 действует правило фазы 2.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Маршрутизация с `IPOnDemand` | два разрешения имени: блок по одному адресу, соединение — по другому |
| Маршрутизация и `finalRules` вместе | две реализации одного правила — против принципа «один путь» |

## Последствия

- `config` перестаёт отрисовывать `blackhole` и правило `ip`; эталоны конфигурации меняются.
- Поле должно существовать во всём проверенном диапазоне Xray: при его расширении сверяется.
- Пересмотреть, если `finalRules` изменят или уберут в upstream.
