# ADR-0021: Проверка владельцем на реальной интеграции

- Статус: Принято
- Дата: 2026-11-16

## Контекст

Часть эффектов не доказывается в CI и в сессии агента: настоящая сеть VPS, клиенты на
Windows 11, ОС владельца вне матрицы L4. До сих пор такое шло в «не проверено» и ждало приёмки
L5 перед релизом. Владелец хочет по каждому такому PR быстро понять, можно ли сливать: получить
один скрипт для VPS или Windows 11, запустить его и по короткому однозначному ответу получить
вердикт. Инвариант 6 запрещает просить сырой вывод с сервера, инвариант 7 — новые публичные
порты, инвариант 9 — инструменты и адреса без согласия.

## Решение

- Субагент `integration-check` после создания PR решает, нужна ли проверка на реальной
  интеграции (по умолчанию — нет), и если нужна — выдаёт скрипт из каркаса
  `scripts/integration/vps.sh` или `scripts/integration/win11.ps1` и ожидаемую строку.
- Скрипт самодостаточен: песочница во временном каталоге, недостающие инструменты — пакетным
  менеджером ОС, коммит — по SHA с проверкой; в конце удаляются песочница и поставленные пакеты.
  Рабочую установку, юниты, фаервол и публичные порты не меняет.
- Скрипт печатает одну строку `XM-CHECK <id> <sha7> PASS|FAIL <шаг> clean|dirty` только из
  открытых данных; остальной вывод остаётся в журнале песочницы и удаляется. Это не сырой вывод
  с сервера: инвариант 6 не меняется.
- В ответе владельцу блок «Нужна проверка на реальной интеграции» есть, только когда она нужна;
  поле «Готово к Pull Request: True | False — причина» — только после присланной строки.
- Контракт — [integration-check.md](../dev/integration-check.md).

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Только приёмка L5 перед релизом | владелец не знает, безопасно ли сливать отдельный PR |
| Скрипт с подробным выводом, который владелец присылает целиком | нарушает инвариант 6; текст длинный, вердикт неоднозначен |
| Скрипт проверки в ветке PR, запуск через загрузку по сети | всё равно нужен самодостаточный загрузчик; запуск скачанного без проверки — хуже вставки текста |
| Windows Sandbox, контейнер или одноразовая ВМ | Windows Sandbox нет в Windows 11 Home, Docker и LXD на VPS не стоят; временный каталог и учёт пакетов работают везде |

## Последствия

- Провал сообщает только имя шага: диагностика — новым скриптом с более мелкими шагами, а не
  чтением журнала.
- Каркас для Windows в сессии агента не исполняется (нет PowerShell): его первая проверка —
  у владельца на Windows 11.
- Пакеты, поставленные скриптом, удаляются, даже если пригодились бы владельцу; обновления
  списков пакетов `apt` остаются.
- Пересмотреть, если проверок станет много и они повторятся: тогда их место — L4 в CI.
