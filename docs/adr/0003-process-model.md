# ADR-0003: Модель процессов без постоянного демона

- Статус: Принято
- Дата: 2026-11-13

## Контекст

Задание требует модульной архитектуры и минимальной нагрузки на VPS. Модульность можно понять
как набор служб, но на 1 vCPU каждая служба — память, поверхность атаки и точка отказа.

## Решение

- Модульность — на уровне пакетов с проверяемыми границами импортов, а не процессов.
- Один развёртываемый файл `xm`. Постоянно на VPS работает только `xray.service`.
- `xm <команда>` — разовый процесс. `xm ui` — процесс по вызову, который сам завершается без
  запросов. Периодические задачи — разовый процесс по systemd-таймеру.
- Параллельные запуски упорядочивает файловая блокировка `/run/xm/lock`.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Постоянный демон `xm` с API | память и открытый слушатель круглосуточно ради редких операций |
| Несколько служб по компонентам | межпроцессное взаимодействие, версии между службами, больше привилегированных процессов |
| Контейнеры | Docker не должен быть обязательным; сотни мегабайт ради одного бинарника |

## Последствия

- В простое `xm` не занимает память и не имеет сетевой поверхности.
- Длительные операции панели живут в памяти процесса `xm ui` и не переживают его завершение —
  поэтому каждая из них транзакция, которую безопасно прервать.
- События «в реальном времени» недоступны: мониторинг дискретный, с шагом таймера.
- Пересмотреть, если появится функция, которой нужен постоянный процесс (например, управляющий
  узел для многих VPS) — отдельным ADR и отдельным режимом.
