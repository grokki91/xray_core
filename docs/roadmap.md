# План реализации

Пять фаз от пустого репозитория до MVP. Фаза — одна крупная задача с проверяемым результатом;
следующая не начинается, пока не выполнены критерии предыдущей. Изменчивое состояние проекта
хранится только здесь, в таблице §1.

## 1. Состояние

Архитектурный фундамент (документы, ADR, инструкции, проверки репозитория) принят. Кода нет.

| Фаза | Название | Результат | Состояние |
|---|---|---|---|
| 1 | Каркас | собирающийся `xm` с границами модулей и основанием | не начата |
| 2 | Ядро и служба | `xm` ставит проверенный Xray и управляет службой | не начата |
| 3 | Профили и первое подключение | клиент подключается по ссылке и QR | не начата |
| 4 | Установка одной командой | чистый VPS → ссылка и QR без вопросов; первый выпуск | не начата |
| 5 | Надёжность и выпуск MVP | обновление с откатом, снимки, диагностика; выпуск 0.1.0 | не начата |

Разделы: [как пользоваться](#2-как-пользоваться-планом) · [фазы](#3-фазы) ·
[критерии MVP](#4-критерии-готовности-mvp) · [после MVP](#5-после-mvp) ·
[прежняя нумерация](#6-прежняя-нумерация).

## 2. Как пользоваться планом

- Единица работы — шаг фазы: один шаг — одна сессия LLM — один PR, по скилу `change` и
  [шаблону брифа](templates/task-brief.md). Сессии достаточно сказать: «выполни следующий шаг
  фазы N по `docs/roadmap.md`». Несколько шагов подряд в одной сессии — по прямому указанию
  владельца, каждый своим PR.
- Порядок шагов — порядок зависимостей, его не меняют. После каждого шага колонка «Состояние»
  в §1 получает отметку вида «шаги 1–3 из 8»; после выполнения критериев фазы — «завершена».
- «Решения владельца до старта» — вопросы из [open-questions.md](open-questions.md) и согласия
  по [реестру зависимостей](dev/dependencies.md) (инструменты, внешние адреса). Сессия не
  выбирает за владельца: получает ответ и записывает его первым шагом фазы.
- «ADR в фазе» — места, где архитектурные документы не называют владельца или способ действия.
  Шаг не закрывает их молча: варианты владельцу, затем ADR (скил `adr`), затем код.
- «Факты upstream» устанавливаются по скилу `xray-upstream` до кода, который на них опирается,
  и записываются в [compatibility.md](compatibility.md).
- Интерфейсы компонентов — [components.md](architecture/components.md); план их не повторяет, а
  называет объём. Чего нет в шагах фазы, в фазе не делается.
- У каждого шага: тест, который без правки падает; `bash scripts/check.sh`; ревью субагентами по
  [code-review.md](dev/code-review.md) §1; документы — по [documentation.md](dev/documentation.md) §3.

## 3. Фазы

### Фаза 1 — Каркас

- **Цель**: собирающийся бинарник `xm` с проверяемыми границами модулей и готовым основанием
  (`platform`, `store`, `redact`, `contract`), поверх которого следующие фазы пишут только
  прикладную логику.
- **Зависимости**: нет.
- **Решения владельца до старта**: Q4 в части имени команды (`xm`); Q5 целиком — CI на GitHub
  Actions и каждая строка [tooling.md](dev/tooling.md) §1. Без согласия на CI шаг 3
  пропускается, а системные тесты фазы 2 заменяет ручная проверка с принятием риска владельцем;
  фаза 4 без CI невыполнима (конвейер выпуска).

Шаги:

1. **Решения.** Ответы на Q4 (имя команды) и Q5 — в ADR; из `open-questions.md` убираются
   решённые вопросы и решённые части (часть Q4 о мосте остаётся); согласованные инструменты — в
   [dependencies.md](dev/dependencies.md) §3.
2. **Модуль и CLI.** `go.mod` с зафиксированной версией Go и без сторонних модулей; `cmd/xm`
   (только сборка зависимостей); `internal/cli` — диспетчер на стандартном `flag`, команды
   `version` и `help`, коды выхода 0 и 2 ([interfaces.md](architecture/interfaces.md) §1).
   Сборка статическая (`CGO_ENABLED=0`, `-trimpath`), версия подставляется при сборке. Тест
   графа импортов по таблице [repository.md](architecture/repository.md) §3. `scripts/check.sh`
   запускает `gofmt`, `go vet`, `go test ./...`.
3. **CI.** Workflow на PR и на `main` выполняет `bash scripts/check.sh`; действия зафиксированы
   по хэшу коммита, права — `contents: read`, секретов нет; согласованные по Q5 сканеры — тем же
   workflow.
4. **`contract`.** Общий конверт, схемы `version` и `error`, флаг `--json`, эталонный JSON каждой
   схемы в тестах ([interfaces.md](architecture/interfaces.md) §2).
5. **`platform`.** Интерфейс порта; поддельная реализация (временный каталог, запись вызовов);
   настоящие `Exec` (закрытый список программ, без оболочки, таймаут), `FS` (атомарная запись,
   права и владельцы, без следования по ссылкам), `Clock`; общий тест одинакового поведения обеих
   реализаций. Остальные части порта (`Systemd`, `Users`, `Net`) добавляются в фазах 2 и 4
   вместе с первым потребителем — сразу в обеих реализациях.
6. **`store`.** Состояние по [data-model.md](architecture/data-model.md) §2: загрузка с проверкой
   схемы, атомарная запись с правами `0600`, межпроцессная блокировка, механизм миграций с
   тестом «старый файл → новый файл».
7. **`redact`.** Реестр точных значений и шаблоны ([secrets.md](security/secrets.md) §3),
   стабильные метки, `Text` и `JSON`, фаззинг; канареечный тест как общий помощник для
   сценариев следующих фаз ([testing.md](testing.md) §4).

- **Критерии готовности**:
  - `go build ./cmd/xm` даёт статический бинарник в бюджете размера;
  - `xm version` и `xm version --json` отвечают с кодом 0, вывод `--json` совпадает с эталоном;
    неизвестная команда — код 2 с подсказкой в stderr;
  - тест границ падает при запрещённом импорте (показано на временном нарушении);
  - канареечный тест находит незарегистрированное значение (показано на временном нарушении);
  - `bash scripts/check.sh` зелёный и включает проверки Go; при согласованном CI пробный PR с
    ошибкой становится красным.
- **Вне фазы**: менеджеры и любые команды, кроме `version` и `help`; выпуск и `install.sh`
  (фаза 4).
- **Читать**: [repository.md](architecture/repository.md); разделы «Основание» и `cli` в
  [components.md](architecture/components.md); [stack.md](architecture/stack.md) §2.

### Фаза 2 — Ядро и служба

- **Цель**: на чистой машине `xm install` с явно заданными параметрами ставит проверенный Xray
  и запускает `xray.service` с конфигурацией, отрисованной из состояния; каждое изменение
  системы — транзакция с откатом.
- **Зависимости**: фаза 1.
- **Решения владельца до старта**: Q1 (пресет по умолчанию; рекомендация — `reality-xhttp`) и
  Q2 (upstream sing-box; рекомендация — принять несовместимость и показывать её) — оба
  закрывают [ADR-0008](adr/0008-presets-and-client-compat.md).
- **ADR в фазе**: контроль и границы отката транзакции — какой компонент проверяет «порт
  слушается» и выполняет самопроверку (`app` не обращается к `platform` напрямую); что
  откатывается помимо снимка состояния и конфигурации (юнит, ссылка `current`); что считается
  контролем для `xm stop`.
- **Факты upstream**: признак стабильного релиза и наличие хэша файла релиза в API GitHub; поля
  и значения по умолчанию входящего для выбранного пресета; допускает ли Xray входящий без
  клиентов; формат вывода нужных подкоманд.

Шаги:

1. **Решения и факты.** Q1 и Q2 — в ADR-0008; факты upstream — в `compatibility.md`.
2. **`update.Source`** (только установка). Последний стабильный релиз и загрузка архива с
   `.dgst`: закрытый список адресов, только HTTPS, отказ при перенаправлении вне списка, предел
   размера, сверка SHA2-256 и SHA2-512, сверка с хэшем из API GitHub, если факт подтверждён,
   кэш с повторной сверкой ([updates.md](operations/updates.md) §1, §3). Адреса — в
   `dependencies.md` §5.
3. **`core`.** Распаковка с защитой от выхода путей, проверка ELF, архитектуры и ответа
   `xray version`; каталоги версий и атомарная ссылка `current`; `Validate` (`xray run -test`);
   закрытый список подкоманд. Стенд L3: тесты получают настоящий бинарник Xray с проверкой
   суммы и кэшем по версии; помощник стенда живёт вне пакетов менеджеров.
4. **`security`.** Ключи REALITY, идентификатор клиента, shortId — из `crypto/rand`, единственной
   точкой; `EnsureBaseline` — пользователь `xray`, каталоги, владельцы и права по манифесту
   ([data-model.md](architecture/data-model.md) §1); директивы изоляции юнита
   ([policy.md](security/policy.md) §3). Аудит — после MVP.
5. **`logging`.** Журнал `xm` на `slog` поверх редактора; раздел `log` конфигурации Xray с
   выключенным журналом доступа. Чтение журнала Xray — фаза 5.
6. **`config`.** Детерминированная отрисовка состояния в конфигурацию; один пресет в
   `config/preset`; маршрутизация с запретом частных, петлевых и link-local адресов назначения;
   раздел `dns` — из состояния (заполняется в фазе 4); атомарная запись, дрейф. Эталон пресета
   проходит `xray run -test` (L3).
7. **`server`.** Предусловия: root, ОС (Ubuntu 22.04 и 24.04; прочее — остановка с кодом 3, пока
   не решён Q8), архитектура, ресурсы, systemd, время, чужая установка; юнит `xray.service` с
   меткой `xm` и изоляцией; управление службой.
8. **`backup` для транзакции.** Снимок (`tar.gz` и манифест SHA-256) и возврат из него с защитой
   путей. Хранение, проверка и команды — фаза 5.
9. **`app`: транзакция.** ADR о контроле и границах отката; каркас по
   [ADR-0005](adr/0005-transactions-and-rollback.md): блокировка → снимок → изменение →
   `xray run -test` → запись → перезапуск → контроль → фиксация или откат; журнал
   незавершённой транзакции и её откат при следующем запуске; код 5. Контроль в этой фазе —
   служба активна без цикла перезапусков, порт слушается; самопроверка добавляется в фазе 3.
10. **Сценарий и команды.** `xm install --sni <домен> --address <адрес> [--port <порт>]`:
    предусловия → ядро → базовая защита → транзакция (состояние, конфигурация, юнит, запуск);
    без `--sni` или `--address` — ошибка с кодом 2 (автоматический выбор — фаза 4). Команды
    `start`, `stop`, `restart`, `status`; схема `status`: служба, версии, адреса и порт, дрейф.
11. **Системный тест L4: каркас.** На размещённых исполнителях Ubuntu 22.04 и 24.04: установка,
    служба, пользователь и возможности процесса Xray, манифест прав. Сценарии следующих фаз
    добавляются сюда же. Скил `system-test`.

- **Критерии готовности**:
  - на чистой Ubuntu 22.04 и 24.04 после `xm install` служба активна от пользователя `xray`,
    порт слушается, `xm status` показывает версию Xray; права совпадают с манифестом (L4);
  - провал на каждом шаге транзакции оставляет исходное состояние (L2 на поддельном `platform`);
  - испорченный архив, неверная сумма, чужой адрес и архив с выходом путей отвергаются до
    установки;
  - одно состояние даёт побайтно одну конфигурацию; эталон проходит `xray run -test`;
  - канареечный тест на командах фазы не находит секретов; память Xray на целевой конфигурации
    VPS измерена и записана.
- **Вне фазы**: профили и ссылки; определение адресов и выбор цели REALITY; `uninstall`;
  обновление и откат версии; команды снимков.
- **Читать**: разделы `core`, `config`, `server`, `security`, `logging`, `update`, `backup`,
  `app` в [components.md](architecture/components.md); [overview.md](architecture/overview.md) §6;
  [updates.md](operations/updates.md) §1–§3; [policy.md](security/policy.md) §3–§6.

### Фаза 3 — Профили и первое подключение

- **Цель**: профиль создаётся одной командой; его ссылка и QR принимаются клиентом; сквозной
  путь доказан автоматическим тестом и подключением настоящего клиента.
- **Зависимости**: фаза 2.
- **Решения владельца до старта**: способ генерации QR — своя реализация или небольшая
  Go-библиотека; тестовый адрес самопроверки (внешний адрес, к которому обращается `xm`).
- **Факты upstream**: как v2rayN и Hiddify разбирают ссылку VLESS — набор и порядок параметров,
  значение `fp` (скил `client-profiles`).

Шаги:

1. **Решения и факты.** Решение по QR и адрес самопроверки — в
   [реестр](dev/dependencies.md) (зависимость — ещё и ADR); факты о разборе ссылок — в
   `compatibility.md`.
2. **`profile`.** Создание, список, показ, удаление; имя по правилу
   `[a-z0-9][a-z0-9_-]{0,31}`; учётные данные — от `security`; изменение — транзакцией.
3. **Экспортёр `uri`.** Ссылка VLESS для IPv4, IPv6 (в скобках) и домена; эталоны на фиктивных
   данных; тест «ссылка → разбор → те же параметры».
4. **`profile/compat`.** Таблица совместимости данными; тест сверки с `compatibility.md` §3;
   экспорт под несовместимый клиент — ошибка с причиной.
5. **Экспортёр `qr`** для терминала: кодирует ровно ту же строку, что показана ссылкой.
6. **Команды.** `add`, `list`, `show`, `rm`; схемы `profiles` и `profile`; `xm install`
   завершается первым профилем — ссылкой и QR; `xm status` показывает число профилей и
   минимальные версии клиентов. Секреты печатают только `install`, `add` и `show`.
7. **Сквозной тест и самопроверка.** L3: сервер из состояния ↔ клиент Xray из экспортированной
   ссылки ↔ тестовый адрес. Тот же механизм — самопроверка в контроле транзакции
   ([updates.md](operations/updates.md) §5), у компонента, названного ADR фазы 2.
8. **Подключение настоящим клиентом.** Владелец ставит сборку на тестовый VPS и подключается
   v2rayN и Hiddify 5.x по ссылке и QR; результат — «проверено на устройстве, дата» в
   `compatibility.md`. Данные установки в репозиторий не попадают.

- **Критерии готовности**:
  - ссылка из `xm add` принимается клиентом Xray в сквозном тесте; ссылка для IPv6 корректна;
  - удалённый профиль перестаёт подключаться;
  - экспорт под несовместимый клиент — ошибка с причиной из таблицы;
  - `xm list` и журналы не содержат секретов (канареечный тест);
  - провал самопроверки откатывает транзакцию;
  - владелец подключился клиентом из таблицы совместимости.
- **Вне фазы**: файл настроек sing-box и другие форматы; QR в SVG; второй пресет; бинарники
  клиентских ядер в тестах.
- **Читать**: раздел `profile` в [components.md](architecture/components.md); скил
  `client-profiles`; [compatibility.md](compatibility.md) §3; [testing.md](testing.md) §3.

### Фаза 4 — Установка одной командой

- **Цель**: одна команда из README на чистой Ubuntu 22.04 или 24.04 заканчивается ссылкой и QR
  без вопросов; повторный запуск ничего не меняет; `xm` распространяется выпуском с проверкой
  суммы.
- **Зависимости**: фазы 2 и 3; согласованный CI.
- **Решения владельца до старта**: Q3 (как выбирать цель REALITY; рекомендация — список
  кандидатов с живой проверкой и необязательный `--sni`); Q7 в части установки (правило UFW,
  если UFW уже активен); Q10 (лицензия); внешние адреса — сервис определения внешнего адреса и
  DoH-серверы по умолчанию.
- **ADR в фазе**: какой компонент ставит и снимает правило UFW и как оно откатывается;
  `uninstall` — сценарий, который каркас транзакции не откатывает (ADR-0005 требует для
  такого ADR).

Шаги:

1. **Решения.** Q3, Q7 (в части установки) и Q10 — в ADR; файл лицензии; адреса — в
   `dependencies.md` §5.
2. **`network`: факты.** Адреса IPv4 и IPv6 по интерфейсам, внешний адрес за NAT (закрытый
   список адресов, `--address` переопределяет), занятость порта, состояние фаервола.
3. **`network`: цель REALITY.** Проверка цели (TLS 1.3, h2, X25519MLKEM768, сертификат) и выбор
   по решению Q3; `--sni` переопределяет.
4. **`dns`.** План раздела `dns` конфигурации: DoH-серверы и стратегия семейств адресов по
   сетевым фактам; эталоны. Проверки резолвинга — после MVP.
5. **`xm install` целиком.** Флаги необязательны; идемпотентность (состояние, конфигурация и
   ключи до и после повторного запуска совпадают); профиль на каждый адрес сервера; правило
   UFW — по ADR этой фазы.
6. **`xm uninstall [--purge]`** по [data-model.md](architecture/data-model.md) §6 и ADR этой
   фазы, с подтверждением вводом слова.
7. **Выпуск и загрузчик.** Конвейер: сборка linux/amd64, `SHA256SUMS`, версия из тега; `install.sh`
   по [ADR-0013](adr/0013-distribution-and-bootstrap.md) — только скачать, сверить, запустить
   `xm install`. Скил `release`.
8. **Системные тесты L4 целиком**: установка настоящим `install.sh`, повторная установка,
   профили, удаление — на Ubuntu 22.04 и 24.04.
9. **README и руководство.** Три варианта установки по ADR-0013; установка по шагам — в
   пользовательском руководстве (каталог `guide` в `docs/`). Проверка на живом VPS владельцем.

- **Критерии готовности**:
  - `install.sh` на чистой Ubuntu 22.04 и 24.04 заканчивается ссылкой и QR без вопросов;
  - повторный запуск ничего не меняет и не перевыпускает ключи; чужая установка Xray не тронута;
  - сервер только с IPv4 и сервер с IPv4 и IPv6 дают корректные профили (L2; на живом сервере —
    проверка владельцем);
  - `uninstall` сохраняет состояние и снимки; `uninstall --purge` не оставляет следов по
    манифесту, посторонние файлы целы;
  - испорченный бинарник `xm` отвергается загрузчиком до установки;
  - L4 зелёный на обеих ОС; опубликован предварительный выпуск 0.0.x.
- **Вне фазы**: `xm update`, диагностика, другие ОС и архитектуры, `xm harden`.

### Фаза 5 — Надёжность и выпуск MVP

- **Цель**: систему можно обновлять, восстанавливать и проверять; выпуск 0.1.0.
- **Зависимости**: фаза 4.
- **Решения владельца до старта**: контрольные узлы диагностики (внешние адреса для проверки
  исходящих соединений); приёмку L5 выполняет владелец.

Шаги:

1. **`xm update`.** Проверенный диапазон версий данными; `--check`, `--to`; удержание; порядок,
   контроль и автоматический откат по [updates.md](operations/updates.md) §4–§6; схема `update`;
   `xm status` показывает доступную версию.
2. **`xm update --rollback`** и системный тест обновления и отката между двумя версиями Xray;
   код 5 с точными шагами, если не проходит и предыдущая версия.
3. **`xm update --self`** по [updates.md](operations/updates.md) §8: тот же источник и та же
   проверка, что у загрузчика; миграция состояния в транзакции; откат при провале.
4. **Снимки.** `xm backup [--list]`, `xm restore <id>`; схема `backups`; хранение и проверка по
   [data-model.md](architecture/data-model.md) §4; тест «снимок → порча → восстановление».
5. **`diag`.** Движок: проверка → наблюдения → правила анализа → выводы → отчёт; точка
   наблюдения `local`; проверки с пометкой MVP из [diagnostics.md](operations/diagnostics.md) §4;
   история отчётов; `xm diag [--only] [--export]`, код 4, схема `diag-report`. Отчёт
   редактируется до сохранения; контрольные узлы — в `dependencies.md` §5.
6. **`xm logs [-f] [--since]`.** Журнал Xray и `xm` из journald; строки журнала — недоверенные.
7. **Документация.** README в один экран команд; пользовательское руководство; чек-лист
   приёмки L5 ([testing.md](testing.md) §7).
8. **Выпуск 0.1.0.** Замер бюджетов ([overview.md](architecture/overview.md) §8); L0–L4 зелёные;
   приёмка L5; критерии §4.

- **Критерии готовности**: критерии MVP (§4).
- **Вне фазы**: всё из §5.

## 4. Критерии готовности MVP

MVP — минимальная версия, которую можно установить и использовать без Web UI.

Функции:

1. Одна команда из README на чистой Ubuntu 22.04 или 24.04 (x86_64) завершается ссылкой VLESS и
   QR-кодом без вопросов.
2. Повторный запуск установки ничего не ломает и не перевыпускает ключи.
3. Работают команды: `install`, `uninstall`, `start`, `stop`, `restart`, `status`, `add`,
   `list`, `show`, `rm`, `update`, `diag`, `logs`, `backup`, `restore`, `version`, `help`.
4. Профиль подключается клиентами v2rayN и Hiddify 5.x — проверено на устройствах (L5).
5. IPv4 и IPv6: сервер слушает оба семейства, профиль выдаётся для каждого адреса.
6. `xm update` обновляет Xray с проверкой сумм и откатывается при провале контроля.
7. `xm diag` выполняет минимальный набор проверок и экспортирует отредактированный отчёт.

Качество:

8. Тесты L0–L4 зелёные на 22.04 и 24.04; канареечный тест не находит секретов в выводе.
9. Xray работает от непривилегированного пользователя; права совпадают с манифестом.
10. В репозитории, выпуске и журналах нет секретов и данных установки.
11. Бюджеты памяти и размера выполнены.
12. README умещается в один экран команд; подробности — в `docs/`.
