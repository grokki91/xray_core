# План реализации

Пять фаз от пустого репозитория до MVP. Фаза — одна крупная задача с проверяемым результатом;
следующая не начинается, пока не выполнены критерии предыдущей. Изменчивое состояние проекта
хранится только здесь, в таблице §1.

## 1. Состояние

Архитектурный фундамент (документы, ADR, инструкции, проверки репозитория) принят. Что сделано —
отметки `✅` у шагов и критериев в §3; состав пакетов — [repository.md](architecture/repository.md)
§1; что покрыто тестами — [testing.md](testing.md) §8. Сводного перечня сделанного здесь нет: его
правил бы каждый шаг, и параллельные шаги конфликтовали бы в одной строке.

## 2. Как пользоваться планом

- Единица работы — шаг фазы: один шаг — одна сессия LLM — один PR, по скилу `change` и
  [шаблону брифа](templates/task-brief.md). Сессии достаточно сказать: «выполни следующий шаг
  фазы N по `docs/roadmap.md`». Несколько шагов подряд в одной сессии — по прямому указанию
  владельца, каждый своим PR.
- Порядок шагов — порядок зависимостей. Строка «Волны» фазы называет, что от чего не зависит:
  шаги в одних скобках можно вести параллельно — разными сессиями, у каждой свой PR (скил
  `orchestrate`); волны идут по порядку. Общие файлы шагов волны (`cli`, `app`, `contract`,
  `platform`) сходятся при слиянии: сессия, чей PR сливается позже, сначала вливает `main`.
- Колонка «Состояние» в §1: «не начата», «в работе» — с первого шага, «✅ завершена» — после
  критериев фазы. Сколько шагов сделано, видно по отметкам в §3: счётчик в таблице не ведётся.
- Задача аудита (§7) имеет идентификатор `A<n>` и приоритет P0–P3; срок — колонка «Когда»
  таблицы §7. P0 закрывается до публикации первого выпуска.
- Выполненное отмечается в той же правке, что его выполнила: шаг или подпункт — `✅` и
  зачёркнутый заголовок (`1. ✅ ~~**Имя.**~~`), выполненный критерий готовности — `✅` в начале
  строки. Текст шага не удаляется. Частично выполненный шаг не отмечается — отмечаются его
  выполненные подпункты.
- У каждой фазы есть issue на GitHub со списком шагов флажками. Пункт шага
  отмечается `[x]` и зачёркивается (`- [x] ~~5. …~~`); после завершения фазы issue закрывается.
  Отметку ставит сессия, выполнившая шаг, сразу после создания его PR — так же, как отметку в плане.
- «Решения владельца до старта» — вопросы из [open-questions.md](open-questions.md) и согласия
  по [реестру зависимостей](dev/dependencies.md) (инструменты, внешние адреса). Сессия не
  выбирает за владельца: получает ответ и записывает его первым шагом фазы.
- «ADR в фазе» — места, где архитектурные документы не называют владельца или способ действия.
  Шаг не закрывает их молча: варианты владельцу, затем ADR (скил `adr`), затем код.
- «Факты upstream» устанавливаются по скилу `xray-upstream` до кода, который на них опирается,
  и записываются в [compatibility.md](compatibility.md).
- Интерфейсы компонентов — [components.md](architecture/components.md); план их не повторяет, а
  называет объём. Чего нет в шагах фазы, в фазе не делается.
- У каждого шага: тест, который без правки падает; `bash scripts/check.sh`; ревью субагентами по
  [code-review.md](dev/code-review.md) §1; документы — по [documentation.md](dev/documentation.md) §3.

## 3. Фазы

### Фаза 1 — Каркас

- **Цель**: собирающийся бинарник `xm` с проверяемыми границами модулей и готовым основанием
  (`platform`, `store`, `redact`, `contract`), поверх которого следующие фазы пишут только
  прикладную логику.
- **Зависимости**: нет.
- **Решения владельца до старта**: Q4 в части имени команды (`xm`); Q5 целиком — CI на GitHub
  Actions и каждая строка [tooling.md](dev/tooling.md) §1. Приняты, CI согласован:
  [ADR-0016](adr/0016-ci-and-tooling.md).

Шаги:

1. ✅ ~~**Решения.**~~ Ответы на Q4 (имя команды) и Q5 — в ADR; из `open-questions.md` убираются
   решённые вопросы и решённые части (остальные части Q4 остаются); согласованные инструменты — в
   [dependencies.md](dev/dependencies.md) §3.
2. ✅ ~~**Модуль и CLI.**~~ `go.mod` с зафиксированной версией Go и без сторонних модулей; `cmd/xm`
   (только сборка зависимостей); `internal/cli` — диспетчер на стандартном `flag`, команды
   `version` и `help`, коды выхода 0 и 2 ([interfaces.md](architecture/interfaces.md) §1).
   Сборка статическая (`CGO_ENABLED=0`, `-trimpath`), версия подставляется при сборке. Тест
   графа импортов по таблице [repository.md](architecture/repository.md) §3. `scripts/check.sh`
   запускает `gofmt`, `go vet`, `go test ./...`.
3. ✅ ~~**CI.**~~ Workflow на PR и на `main` выполняет `bash scripts/check.sh`; действия зафиксированы
   по хэшу коммита, права — `contents: read`, секретов нет ([policy.md](security/policy.md) §6);
   правило ветки `main` требует эту проверку (включает владелец); согласованные по
   [ADR-0016](adr/0016-ci-and-tooling.md) сканеры — тем же workflow.
4. ✅ ~~**`contract`.**~~ Общий конверт, схемы `version` и `error`, флаг `--json`, эталонный JSON каждой
   схемы в тестах ([interfaces.md](architecture/interfaces.md) §2).
5. ✅ ~~**`platform`.**~~ Интерфейс порта; поддельная реализация (временный каталог, запись вызовов);
   настоящие `Exec` (закрытый список программ, без оболочки, таймаут), `FS` (атомарная запись,
   права и владельцы, без следования по ссылкам), `Clock`; общий тест одинакового поведения обеих
   реализаций. Остальные части порта (`Systemd`, `Users`, `Net`) добавляются в фазах 2 и 4
   вместе с первым потребителем — сразу в обеих реализациях.
6. ✅ ~~**`store`.**~~ Состояние по [data-model.md](architecture/data-model.md) §2: загрузка с проверкой
   схемы, атомарная запись с правами `0600`, межпроцессная блокировка, механизм миграций с
   тестом «старый файл → новый файл».
7. ✅ ~~**`redact`.**~~ Реестр точных значений и шаблоны ([secrets.md](security/secrets.md) §3),
   стабильные метки, `Text` и `JSON`, фаззинг; канареечный тест как общий помощник для
   сценариев следующих фаз ([testing.md](testing.md) §4).

- **Критерии готовности**:
  - ✅ `go build ./cmd/xm` даёт статический бинарник в бюджете размера;
  - ✅ `xm version` и `xm version --json` отвечают с кодом 0, вывод `--json` совпадает с эталоном;
    неизвестная команда — код 2 с подсказкой в stderr;
  - ✅ тест границ падает при запрещённом импорте (показано на временном нарушении);
  - ✅ канареечный тест находит незарегистрированное значение (показано на временном нарушении);
  - ✅ `bash scripts/check.sh` зелёный и включает проверки Go; пробный PR с ошибкой становится
    красным и не может быть слит в `main`.
- **Вне фазы**: менеджеры и любые команды, кроме `version` и `help`; выпуск и `install.sh`
  (фаза 4).
- **Читать**: [repository.md](architecture/repository.md); разделы «Основание» и `cli` в
  [components.md](architecture/components.md); [stack.md](architecture/stack.md) §2.

### Фаза 2 — Ядро и служба

- **Цель**: на чистой машине `xm install` с явно заданными параметрами ставит проверенный Xray
  и запускает `xray.service` с конфигурацией, отрисованной из состояния; каждое изменение
  системы — транзакция с откатом.
- **Зависимости**: фаза 1.
- **Решения владельца до старта**: Q1 (пресет по умолчанию — `reality-xhttp`) и Q2 (upstream
  sing-box не поддерживается, несовместимость показывается). Приняты:
  [ADR-0008](adr/0008-presets-and-client-compat.md).
- **ADR в фазе**: контроль и границы отката транзакции — какой компонент проверяет «порт
  слушается» и выполняет самопроверку (`app` не обращается к `platform` напрямую); что
  откатывается помимо снимка состояния и конфигурации (юнит, ссылка `current`); что считается
  контролем для `xm stop`.
- **Факты upstream**: признак стабильного релиза и наличие хэша файла релиза в API GitHub; поля
  и значения по умолчанию входящего для выбранного пресета; допускает ли Xray входящий без
  клиентов; формат вывода нужных подкоманд.
- **Волны**: шаги 1–9 → 10 → 11.

Шаги:

1. ✅ ~~**Решения и факты.**~~ Q1 и Q2 — в ADR-0008; факты upstream — в `compatibility.md`.
2. ✅ ~~**`update.Source`**~~ (только установка). Последний стабильный релиз и загрузка архива с
   `.dgst`: закрытый список адресов, только HTTPS, отказ при перенаправлении вне списка, предел
   размера, сверка SHA2-256 и SHA2-512, сверка с хэшем из API GitHub, если факт подтверждён,
   кэш с повторной сверкой ([updates.md](operations/updates.md) §1, §3). Адреса — в
   `dependencies.md` §5.
3. ✅ ~~**`core`**~~ — двумя PR по решению владельца 2026-11-16
   ([ADR-0019](adr/0019-versioned-xray-exec-and-current-link.md)).
   - ✅ ~~3a.~~ Распаковка с защитой от выхода путей, проверка ELF, архитектуры и ответа
     `xray version`; каталоги версий и атомарная ссылка `current`; `Validate` (`xray run -test`);
     закрытый список подкоманд — на поддельном `platform`.

   точкой; `EnsureBaseline` — пользователь `xray`, каталоги, владельцы и права по манифесту

6. ✅ ~~**`config`.**~~ Детерминированная отрисовка состояния в конфигурацию; один пресет в
   `config/preset`; маршрутизация с запретом частных, петлевых и link-local адресов назначения;

7. ✅ ~~**`server`.**~~ Предусловия: root, ОС (Ubuntu 22.04 и 24.04; прочее — остановка с кодом 3, пока

8. ✅ ~~**`backup` для транзакции.**~~ Снимок (`tar.gz` и манифест SHA-256) и возврат из него с защитой
   путей. Хранение, проверка и команды — фаза 5.
9. ✅ ~~**`app`: транзакция.**~~ ADR о контроле и границах отката; каркас по
   [ADR-0005](adr/0005-transactions-and-rollback.md): блокировка → снимок → изменение →
   `xray run -test` → запись → перезапуск → контроль → фиксация или откат; журнал
   незавершённой транзакции и её откат при следующем запуске; код 5. Контроль в этой фазе —
   служба активна без цикла перезапусков, порт слушается; самопроверка добавляется в фазе 3.
10. ✅ ~~**Сценарий и команды.**~~ `xm install --sni <домен> --address <адрес> [--port <порт>]`:
    предусловия → ядро → базовая защита → транзакция (состояние, конфигурация, юнит, запуск);
    без `--sni` или `--address` — ошибка с кодом 2 (автоматический выбор — фаза 4). Команды
    `start`, `stop`, `restart`, `status`; схема `status`: служба, версии, адреса и порт, дрейф.
11. ✅ ~~**Системный тест L4: каркас.**~~ На размещённых исполнителях Ubuntu 22.04 и 24.04: установка,
    служба, пользователь и возможности процесса Xray, манифест прав. Сценарии следующих фаз
    добавляются сюда же. Скил `system-test`.

- **Критерии готовности**:
  - ✅ на чистой Ubuntu 22.04 и 24.04 после `xm install` служба активна от пользователя `xray`,
    порт слушается, `xm status` показывает версию Xray; права совпадают с манифестом (L4);
  - ✅ провал на каждом шаге транзакции оставляет исходное состояние (L2 на поддельном `platform`);
  - ✅ испорченный архив, неверная сумма, чужой адрес и архив с выходом путей отвергаются до
    установки;
  - ✅ одно состояние даёт побайтно одну конфигурацию; эталон проходит `xray run -test`;
  - ✅ канареечный тест на командах фазы не находит секретов; память Xray на целевой конфигурации

- **Вне фазы**: профили и ссылки; определение адресов и выбор цели REALITY; `uninstall`;
  обновление и откат версии; команды снимков.
- **Читать**: разделы `core`, `config`, `server`, `security`, `logging`, `update`, `backup`,

**A1. Запрет частных адресов доказан на трафике.**
- Проблема: правило `ip` → `blackhole` с `IPOnDemand` проверено только `xray run -test`; для домена
  имя разрешается дважды, между разрешениями ответ может измениться (Q12 решён: [ADR-0027](adr/0027-private-destinations-via-final-rules.md)).
- Зачем: угроза T3 — клиент VPN достаёт службы самого сервера, позже — панель и API на петле.
- Результат: `finalRules` по ADR-0027 вместо правила маршрутизации; запрет доказан тестом на трафике.
- Приёмка: L3 через петлю — запрос клиента к `127.0.0.1`, к частному адресу и к имени, которое
  разрешается в петлевой адрес, не доходит до локального слушателя; «падает без правила» — тест
  отрисовки (L2): встроенный запрет `freedom` не даёт упасть тесту на трафике ([ADR-0034](adr/0034-own-final-rules-over-upstream-default.md)).
  ✅ Сделано: `TestL3PrivateDestinationsBlocked` (петля, `0.0.0.0`, `localhost`; частный адрес и
  `::1` — где они есть у машины) и `TestRenderBlocksPrivateDestinations`.
- Зависимости: стенд сквозного теста (фаза 3, шаг 7).
- Сложность: M. Риски: `finalRules` ведёт себя иначе на границах проверенного диапазона.
- Исполнитель: `implementer`; факт — `upstream-researcher`; ревью — `security-reviewer`.

**A2. Вердикт здоровья и один набор проверок.**
- Проблема: «служба активна, порт слушается, самопроверка» нужны контролю транзакции, `xm status`
  и `xm diag`, а владелец самопроверки не назван (ADR-0023 оставил её фазе 3: `server` не может
  импортировать `core`, `config` и `profile`); отчёт не сводится к одной строке; диагностика —

- Результат: решение по [ADR-0024](adr/0024-health-verdict-and-shared-checks.md) (Q13, принят 2026-11-17):

  фазы 5.
- Приёмка: `xm install` и `xm status` заканчиваются строкой вердикта; провал самопроверки
  откатывает транзакцию; правило вердикта покрыто тестом «гипотеза вердикт не меняет».
- Зависимости: фаза 3, шаг 2.
- Сложность: L. Риски: фаза 3 растёт на один-два шага; поле `health` — изменение схем `status`
  и `diag-report`.
- Исполнитель: `implementer`; ревью — `architecture-reviewer`.

  3. ✅ ~~**Вердикт для владельца.**~~ Поле `health` схемы `status` (`minor + 1`); `xm install` и

- Результат: `network.Facts` различает «входящий порт разрешён локально», «запрещён» и «не
  определено» для UFW и для правил nftables/iptables; итог `xm install` говорит, что доступность
  извне не проверена, и называет действие. Шаг 2 (решение владельца 2026-11-23): три состояния
  для UFW; вне UFW — `iptables`/`ip6tables` вместо `nft` (на образе Ubuntu 24.04 `nft` нет):
  «разрешён» при политике ACCEPT без правил с иной целью, иначе «не определено» — без разбора
  правил запрет не доказан; правила только в своих таблицах nftables не видны. Итог — шаг 5.
- Приёмка: L2 — три состояния локального фаервола дают три разных итога; запрещённый порт —
  факт с командой исправления, а не успех; вывод о фаерволе хостера — не выше гипотезы.
  ✅ Сделано: `TestFirewallStates`, `TestInstallNamesCommandForIptables`,
  `TestInstallNamesCommandForUFWDeny`, `TestInstallFirewallOutcomes`.
- Зависимости: [ADR-0036](adr/0036-install-changes-only-own.md) (правила вне UFW не меняются — факт и команда); фаза 4, шаг 2.
- Сложность: M. Риски: разбор правил netfilter хрупок — читать счётчики политики, не весь набор.
- Исполнитель: `implementer`; ревью — `security-reviewer`.

✅ ~~**A4. Хранение автоснимков до первого выпуска.**~~
- Проблема: снимок с секретами создаётся перед каждой транзакцией, а удаление старых (`Prune`,
  10 автоматических) стоит в фазе 5 — после первого выпуска 0.0.x.
- Зачем: бюджет диска ([overview.md](architecture/overview.md) §8) и число копий секретов.
- Результат: предел автоснимков действует с первого выпуска.
- Приёмка: L2 — одиннадцатая транзакция оставляет десять автоснимков; снимок незавершённой
  транзакции не удаляется.
- Зависимости: нет. Сложность: S. Риски: удаление снимка, на который ссылается журнал транзакции.
- Исполнитель: `implementer`; ревью — `security-reviewer`.

✅ ~~**A5. Контроль перезапусков и остановленная служба.**~~
- Проблема: контроль требует `NRestarts=0` — не проверено, сбрасывает ли счётчик ручной
  перезапуск службы, падавшей раньше; транзакция всегда перезапускает службу — `xm add` после
  `xm stop` молча поднимет VPN.
- Зачем: ложный провал контроля откатывает исправное изменение; запуск остановленной службы —
  действие, которого владелец не просил.
- Результат: поведение счётчика — факт в `compatibility.md` по systemd 249 и 255; выбор владельца
  по остановленной службе записан в ADR шага 10.
- Приёмка: L4 — служба, падавшая до изменения, проходит контроль после `xm restart`; L2 —
  изменение при остановленной службе ведёт себя по ADR.
- Зависимости: фаза 2, шаги 10 и 11. Сложность: S. Риски: нет.
- Исполнитель: `implementer`; факт — `upstream-researcher`.

✅ ~~**A6. `publish-guard` проверяет рабочее дерево исполнителя.**~~
- Проблема: хук запускает `scripts/check.sh` из каталога проекта, а не из рабочего дерева, где
  исполнитель делает коммит: проверяется не то дерево.
- Зачем: параллельные исполнители одной сессии работают в отдельных рабочих деревьях (скил
  `orchestrate`).
- Результат: хук берёт корень из поля `cwd` входа, если это рабочее дерево того же репозитория
  (общий каталог git совпадает); чужой репозиторий корень не подменяет.
- Приёмка: сценарии в `tests/test-guards.sh` — находка в рабочем дереве останавливает коммит;
  каталог чужого репозитория с пустым `check.sh` проверку не обходит.
- Зависимости: нет. Сложность: S. Риски: правка механизма надзора — делает владелец или сессия с
  его явным разрешением; до неё части одной задачи выполняются подряд.
- Исполнитель: владелец или `implementer` с разрешением; ревью — `security-reviewer`.

✅ ~~**A8. Политика исходящего трафика клиентов.**~~
