# Стратегия тестирования

## 1. Принципы

1. **Тест доказывает эффект правки**: с откаченной правкой он падает. Тест ради покрытия или
   зелёного прогона не пишется.
2. Падающий тест не ослабляется, не удаляется и не обходится; ожидание существующего теста
   меняется только как осознанная смена поведения — с причиной в описании PR.
3. Подделка (fake) допустима там, где подменяемое — не предмет проверки. Эффект в поведении
   системы проверяется на настоящей системе.
4. Чего тестами доказать нельзя (поведение в реальных сетях, на устройствах клиентов), так и
   пишется: «не проверено», с командой для ручной проверки.
5. Аномально лёгкий успех — повод искать тихий провал: тест, который не запускался, проверку,
   которая ничего не сравнивает.

## 2. Уровни

| Уровень | Что | На чём | Когда запускается |
|---|---|---|---|
| L0 — статика | форматирование, `go vet`, сканер чувствительных данных, ссылки и бюджеты инструкций | исходники | каждый коммит (`scripts/check.sh`) |
| L1 — модульные | чистая логика: отрисовка конфигурации, экспорт профилей, редактор, миграции состояния, правила анализа диагностики, сравнение версий, проверка сумм | память | каждый коммит |
| L2 — компонентные | сценарии `app` и менеджеры на поддельном `platform`: идемпотентность установки, транзакция и откат, обновление и откат, снимок и восстановление | временный каталог | каждый коммит |
| L3 — интеграция с Xray | настоящий бинарник Xray: `xray run -test` на каждой отрисованной конфигурации; сквозной тест через петлю «сервер из состояния ↔ клиент из экспортированного профиля ↔ локальный HTTP-сервер» | CI и локально, бинарник из кэша | каждый PR; для границ проверенного диапазона версий |
| L4 — системные | настоящий `install.sh` и `xm` на чистой машине с systemd: установка, повторная установка, профили, обновление и откат между двумя версиями, снимок и восстановление, удаление | виртуальная машина | каждый PR, меняющий установку, обновление, юнит, права; перед релизом |
| L5 — приёмка | живой VPS и настоящие клиенты | вручную, владелец | перед релизом, по чек-листу |

Виртуальные машины для L4 — вопрос инструмента ([tooling.md](dev/tooling.md)): размещённые
исполнители GitHub Actions с Ubuntu 22.04 и 24.04 — полноценные машины с systemd и root. Для
26.04 и 20.04 — по наличию образа, иначе вручную.

## 3. Что обязательно покрыто

| Область | Обязательные сценарии |
|---|---|
| Конфигурация | эталонные файлы для каждого пресета; одинаковое состояние → побайтно одинаковый файл; каждый эталон проходит `xray run -test` (L3) |
| Профили | имя: допустимые и вредные значения; экспорт для IPv4, IPv6 (в скобках), домена; ссылка разбирается обратно в те же параметры; экспорт под неподдерживаемый клиент — ошибка |
| Транзакция | провал на каждом шаге оставляет систему в исходном состоянии; незавершённая транзакция откатывается при запуске |
| Установка | повторный запуск ничего не меняет (сравнение состояния, конфигурации, ключей до и после); чужая установка не тронута |
| Обновление | испорченный архив, неверная сумма, чужой адрес, архив с выходом путей — отказ до переключения; провал контроля — откат |
| Снимки | снимок → порча состояния → восстановление возвращает исходное; повреждённый архив отвергается |
| Удаление | без `--purge` состояние и снимки на месте; с `--purge` — пусто по манифесту; посторонние файлы целы |
| Диагностика | у каждой проверки — тест на `ok`, `fail`, `skip`; правила классов: вывод о фильтрации не получает `fact` ни при каком наборе наблюдений |
| Контракт | эталонный JSON каждой схемы; добавление поля не ломает старого потребителя |
| Границы модулей | тест графа импортов по таблице [repository.md](architecture/repository.md) §3 |

## 4. Тесты безопасности

- **Канареечный**: сценарии L2 и L4 выполняются с узнаваемыми значениями секретов; затем весь
  вывод, журналы, отчёты, экспорт и сообщения об ошибках проверяются на их отсутствие.
- **Манифест прав**: после установки и после каждой транзакции владельцы и права совпадают с
  [data-model.md](architecture/data-model.md) §1.
- **Вредный ввод**: метасимволы оболочки, `../`, управляющие последовательности, слишком
  длинные значения — во все точки ввода CLI и API.
- **Фаззинг** (встроенный в Go): редактор, разбор ссылок, разбор `.dgst`, чтение архивов.
- **Привилегии** (L4): процесс Xray — от пользователя `xray` с одной возможностью; панель не
  слушает публичные адреса; через тоннель недостижимы `127.0.0.1` и частные сети.
- **API панели**: запрос без сессии, с чужим `Host`, с чужим `Origin` — отказ.

## 5. Тестовые данные

Только фиктивные значения ([secrets.md](security/secrets.md) §4). Ключи создаются во время
теста. Бинарники Xray для L3 и L4 скачиваются с проверкой суммы и кэшируются по версии; версии —
нижняя и верхняя границы проверенного диапазона.

## 6. Ресурсы

Бюджеты [overview.md](architecture/overview.md) §8 проверяются измерением: память `xm ui` и
разовой команды, размер бинарника, время `xm status`. Превышение — провал релизной проверки.

## 7. Приёмка на живом VPS (L5)

Чек-лист релиза, выполняет владелец: установка одной командой на чистый VPS; подключение
клиентами из таблицы [compatibility.md](compatibility.md) (v2rayN, Hiddify) по ссылке и QR;
IPv4 и IPv6; обновление и откат; `xm diag`; панель через SSH-туннель. Результат —
«проверено на устройстве, дата» в таблице совместимости. Данные установки в репозиторий не
попадают.

## 8. До появления кода

Сейчас тестами покрыты только проверки репозитория и хуки (`tests/test-guards.sh`). Уровни
L1–L4 вводятся вместе с кодом по фазам [roadmap.md](roadmap.md).
