# Политика безопасности

Обязательна для кода, документации и любых действий агентов. Секреты — отдельно:
[secrets.md](secrets.md). Сообщить об уязвимости — [SECURITY.md](../../SECURITY.md).

## 1. Модель угроз

Защищаем: доступ владельца к серверу (SSH), ключи и профили, работоспособность VPN, анонимность
установки (адрес сервера, цель REALITY), целостность бинарников.

| № | Нарушитель или ошибка | Что может | Чем отвечаем |
|---|---|---|---|
| T1 | Сканер, активный зонд | опрашивает открытый порт | открыт только порт Xray; панель и API — на петле (§4) |
| T2 | Наблюдатель на пути (DPI) | анализирует и режет трафик | вне гарантий: не обещаем обход; диагностика измеряет, а не утверждает ([diagnostics.md](../operations/diagnostics.md)) |
| T3 | Клиент VPN | идёт через тоннель к службам самого сервера | запрет частных и петлевых адресов назначения в маршрутизации Xray (§4) |
| T4 | Локальный процесс или пользователь VPS | читает файлы, ходит на петлю | права по манифесту, токен и сессия панели, API Xray только со статистикой (§3, §4) |
| T5 | Подмена при доставке | портит загрузку, кэш, зависимость | суммы, закрытый список источников, реестр зависимостей (§6) |
| T6 | Утечка при публикации | секреты в репозитории, PR, журнале, отчёте, чате LLM | [secrets.md](secrets.md), редактор, хуки |
| T7 | Ошибка владельца или агента | ломает конфигурацию, теряет доступ, удаляет данные | транзакции, снимки, подтверждения (§7, §8) |
| T8 | Скомпрометированный upstream-релиз | вредоносный бинарник с верными суммами | не закрывается полностью: диапазон проверенных версий, ручное обновление, пользователь без привилегий (§3, §6) |

## 2. Требования и меры

| Требование | Мера | Где | Чем проверяется |
|---|---|---|---|
| Нет секретов в Git | только фиктивные данные; сканер | `scripts/guard.sh`, хуки | `scripts/check.sh` |
| Нет секретов в README, комментариях, логах, PR | редактор в журнале и отчётах; проверка текста публикации | `redact`, `logging`, хук `publish-guard` | канареечный тест ([testing.md](../testing.md) §4) |
| Безопасная генерация и хранение ключей | `crypto/rand`, один источник, права `0600` | `security`, `store` | тест манифеста прав |
| Автоматическая настройка прав | манифест и `EnsureBaseline` при каждой транзакции | `security` | тест L2 и системный тест |
| Минимальные привилегии | §3 | юнит, `platform` | системный тест: пользователь и возможности процесса |
| Защита SSH и системных служб | аудит всегда; изменение — отдельной командой с защитой от потери доступа | `security` (§7) | системный тест |
| Проверка бинарников и сумм | SHA-256 и SHA-512, проверка ELF и версии | `update`, `core` (§6) | тесты с испорченным архивом |
| Контроль источников обновлений | закрытый список адресов, только HTTPS | `update` | тест: чужой адрес отвергается |
| Безопасное применение конфигураций | транзакция, `xray run -test` до записи | `app`, `config` | тест отката |
| Резервное копирование и восстановление | автоснимок перед транзакцией | `backup` | тест «снимок → порча → восстановление» |
| Защита от случайного удаления | §8 | `cli`, `app` | тест сценариев удаления |
| Безопасная обработка ввода | §5 | `cli`, `api`, `platform` | тесты с вредным вводом, фаззинг |

## 3. Привилегии

- Xray работает от системного пользователя `xray` без оболочки и домашнего каталога; из
  возможностей — только `CAP_NET_BIND_SERVICE`.
- Юнит изолирован директивами systemd: `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`,
  `PrivateTmp`, `PrivateDevices`, `ProtectKernelTunables`, `ProtectKernelModules`,
  `ProtectControlGroups`, `RestrictAddressFamilies` (IPv4, IPv6, UNIX), `RestrictNamespaces`,
  `LockPersonality`, `MemoryDenyWriteExecute`, `SystemCallArchitectures=native`. Точный набор
  подтверждается на каждой поддерживаемой ОС системным тестом: служба стартует и держит соединение.
- `xm` требует root только для изменяющих команд и говорит об этом сразу (код выхода 3).
- `xm` не создаёт setuid-файлов, не правит `sudoers` (исключение — правило моста, отдельной
  командой после MVP) и не меняет пользователей, кроме `xray`.

## 4. Сетевая поверхность

| Что слушает | Где | Защита |
|---|---|---|
| Xray, входящий | публичный порт (443) | протокол и REALITY upstream |
| Панель и HTTP API | `127.0.0.1`, только пока запущен `xm ui` | разовый токен → сессия, проверка `Host` и `Origin`, самозавершение |
| API Xray (статистика) | `127.0.0.1` | включён только StatsService; учёт адресов клиентов выключен |

- Административный интерфейс не слушает публичные адреса; флага «открыть наружу» нет.
- В маршрутизации Xray адреса назначения из частных, петлевых и link-local сетей (IPv4 и IPv6)
  уходят в `blackhole` — списком CIDR в конфигурации, без файлов geodata. Без этого правила
  клиент VPN достаёт до панели и API через тоннель.
- Новых открытых портов расширения не добавляют: удалённое управление и мост идут по SSH.

## 5. Пользовательский ввод

- Каждое значение проверяется по закрытому правилу до использования: имя профиля —
  `[a-z0-9][a-z0-9_-]{0,31}`, порт — 1…65535, домен — синтаксис имени хоста, адрес — разбор
  `netip`, версия — `N.N.N`, идентификатор снимка — из списка существующих.
- Процессы запускаются массивом аргументов без оболочки; ввод никогда не становится именем
  программы или частью строки команды.
- Пути из ввода не принимаются, кроме `--export <файл>`: запись без следования по ссылкам и без
  перезаписи существующего файла.
- Архивы (релиз, снимок) распаковываются с проверкой, что каждый путь остаётся в каталоге
  назначения; размер и число файлов ограничены.
- Строки из журналов и ответов сети — недоверенные: в терминал — без управляющих
  последовательностей, в страницу — только `textContent`.

## 6. Цепочка поставки

- **Xray-core**: только релизы `XTLS/Xray-core` на GitHub, только HTTPS, канал — стабильные
  релизы. Порядок проверки — [updates.md](../operations/updates.md) §3. Upstream публикует хэши,
  но не подписи: сумма защищает от порчи при доставке и в кэше, но не от подмены самого релиза (T8).
- **`xm`**: релизы этого репозитория, бинарник и `SHA256SUMS`. Сборка воспроизводимая
  (`-trimpath`, без cgo). Подтверждение происхождения сборки (attestation) — с первым
  выпуском (фаза 4, [ADR-0016](../adr/0016-ci-and-tooling.md)).
- **`install.sh`**: только скачивает, сверяет SHA-256 и запускает `xm install`; тело — в функции,
  вызываемой последней строкой (обрыв загрузки не исполняет половину скрипта). В README рядом с
  командой в одну строку — вариант «скачать, прочитать, запустить» и вариант с фиксированной версией.
- **Зависимости**: цель MVP — ноль сторонних Go-модулей. Любая зависимость, инструмент или
  действие CI — только с согласия владельца и строкой в [реестре](../dev/dependencies.md);
  действия CI фиксируются по хэшу коммита.
- **CI** ([ADR-0016](../adr/0016-ci-and-tooling.md)):
  - события — только `pull_request`, `push` в `main` и `push` тега `v*` (последнее — только для
    задания выпуска); `pull_request_target` и `workflow_run` запрещены;
  - `permissions: contents: read` на уровне workflow; расширенные права (`id-token`,
    `attestations`, `contents: write`) — только у задания выпуска, никогда на PR; секретов в
    заданиях проверок нет;
  - данные события (заголовок, ветка, тело PR) — в шаги только через `env:`, без подстановки
    `${{ }}` в текст `run:`;
  - `actions/checkout` — с `persist-credentials: false`; для gitleaks — полная история;
  - gitleaks — с `--ignore-gitleaks-allow`, без `.gitleaksignore` и без своих списков
    разрешённых значений в конфигурации; встроенные правила — как есть;
  - бинарники сканеров — только из релизов их репозиториев на GitHub по HTTPS, сумма SHA-256
    записана в workflow и сверяется до первого запуска, расхождение останавливает задание;
  - модули Go — через прокси и `sum.golang.org`; `GOSUMDB`, `GONOSUMDB`, `GOINSECURE` не
    переопределяются;
  - проверка `check.sh` обязательна для слияния в `main` (правило ветки включает владелец).
- **Системные пакеты**: `xm install` не ставит пакеты ОС. Нужная утилита отсутствует —
  остановка с названием пакета.

## 7. SSH, фаервол, системные службы

- По умолчанию `xm` только смотрит: аудит (`security.Audit`) показывает вход root по паролю,
  разрешённые пароли, состояние фаервола и автоматических обновлений ОС — как наблюдения в
  `xm diag` с готовыми командами исправления.
- Единственное автоматическое изменение фаервола при установке: если UFW активен — правило для
  порта Xray; оно входит в транзакцию и снимается при удалении.
- Изменение настроек SSH и включение фаервола — команда `xm harden` (после MVP, отдельный ADR,
  вопрос Q7) с защитой от потери доступа: проверка входа по ключу, `sshd -t`, текущая сессия
  не рвётся, изменение само откатывается, если владелец не подтвердил его из новой сессии.

## 8. Защита от случайного удаления и порчи

- `xm` изменяет и удаляет только пути из манифеста ([data-model.md](../architecture/data-model.md) §1).
- Чужая установка Xray (служба или конфигурация без метки `xm`) не перезаписывается: остановка
  с объяснением (код 3).
- `uninstall` без `--purge` сохраняет состояние и снимки; `--purge`, `restore`,
  `install --reinstall` требуют флага и подтверждения вводом слова.
- Перегенерация ключей (все выданные ссылки перестают работать) — только явной командой с тем же
  подтверждением; повторная установка ключи не трогает.
- Перед каждой транзакцией — снимок; незавершённая транзакция откатывается при следующем запуске.

## 9. Что считается нарушением политики

Изменение не сливается, если оно: добавляет сетевой слушатель вне §4; запускает процесс через
оболочку; пишет на диск мимо манифеста; выводит данные мимо редактора; добавляет зависимость без
реестра; ослабляет изоляцию юнита или проверку сумм без ADR. Проверяет субагент
`security-reviewer` и ревью владельца ([code-review.md](../dev/code-review.md)).
