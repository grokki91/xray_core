# Политика работы с секретами

Главное правило: **секреты создаются и живут только на VPS**. В репозитории, PR, журналах,
отчётах и переписке с LLM их нет.

## 1. Что считается чувствительным

| Класс | Примеры | Где может находиться |
|---|---|---|
| S1 — учётные данные | приватный ключ REALITY, идентификаторы (UUID) клиентов, shortId, токен и сессия панели, готовые ссылки `vless://` | `state.json`, `config.json`, снимки; экран владельца по его команде |
| S2 — данные установки | адрес и домен сервера, хостер, цель REALITY и её SNI, нестандартный порт, путь XHTTP, адреса клиентов, имя хоста | там же; в отчётах — только в отредактированном виде |
| S3 — открытое | версии, имена пресетов, идентификаторы проверок, коды ошибок | где угодно |

Профиль установки, собранный из мелочей S2, сам по себе утечка: он позволяет найти сервер.
SSH-ключи владельца `xm` не читает и не создаёт.

## 2. Жизненный цикл

| Этап | Правило |
|---|---|
| Создание | на VPS, из `crypto/rand`, единственной точкой — пакетом `security`; значения по умолчанию и «временные» ключи в коде запрещены |
| Хранение | `state.json` (`0600`, root), производный `config.json` (`0640`, root:xray), снимки (`0600`) |
| Показ | только команды, чьё назначение — показать (`xm add`, `xm show`, экран профиля в панели); ответ панели с секретом — `no-store` |
| Передача процессу | файлом или stdin; никогда аргументом командной строки (виден в списке процессов) и не переменной окружения |
| Журналы | секрет не передаётся в журнал даже на уровне отладки; журнал пишется поверх редактора |
| Диагностика и экспорт | отчёт редактируется до сохранения на диск; `xm diag --export` — единственный одобренный способ вынести данные с сервера |
| Резервные копии | остаются на VPS; выгрузка — осознанной командой владельца (после MVP, с шифрованием) |
| Замена | перегенерация ключей — явная команда с подтверждением; удаление профиля сразу убирает его из конфигурации |
| Удаление | `uninstall --purge` удаляет все файлы с секретами по манифесту |

## 3. Редактор

Пакет `redact` — обязательный фильтр на границе «система → человек или файл».

- **Точные значения**: при загрузке состояния в реестр попадают все S1 и S2 (ключи,
  идентификаторы, shortId, адреса, домены, путь). Замена — стабильная метка вида `<uuid:1>`,
  `<server-ip>`: одинаковое значение даёт одинаковую метку, отчёт остаётся читаемым.
- **Шаблоны** — для значений, которых нет в состоянии (адреса клиентов в журнале Xray, чужие
  ссылки): публичные IPv4 и IPv6, UUID, ключи в 43 символа base64url, ссылки `vless://` и подобные.
- Новый вид секрета регистрируется в редакторе в той же правке, где он появляется.
- Редактор проверяется канареечным тестом: сценарии прогоняются с заведомо узнаваемыми
  значениями, и ни одно не должно встретиться в журналах, отчётах, экспорте и сообщениях об
  ошибках ([testing.md](../testing.md) §4).

## 4. Репозиторий: только фиктивные данные

| Что | Допустимые значения |
|---|---|
| IPv4 | `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24` (RFC 5737); частные и петлевые сети; общеизвестные публичные резолверы |
| IPv6 | `2001:db8::/32` (RFC 3849) |
| Домен | `example.com`, `example.org`, `example.net` |
| UUID | начинается с `00000000-0000-`, например `00000000-0000-4000-8000-000000000001` |
| Ключ REALITY в документах и фикстурах | заглушка из 43 символов `A` |
| Ключи в тестах | создаются во время теста, в файлы не попадают |
| shortId | `0123456789abcdef` |
| Порт | 443 |

Запрещено в коде, комментариях, тестах, фикстурах, документах, коммитах, PR и обращениях:

- любые S1 и S2 реальной установки;
- вывод команд с сервера как есть (`journalctl`, `ss`, `ip`, дампы, снимки экрана с адресами);
- файлы `.env`, `*.pem`, `*.key`, `state.json`, боевой `config.json`; шаблоны называются
  `*.example` или `*.tmpl`.

Найденное убирается, а не обходится: исключений и списков разрешённых значений в сканере нет.

## 5. Автоматика

| Момент | Что срабатывает | Что делает |
|---|---|---|
| Запись файла агентом | хук `write-guard` | отказ при секрете в тексте или запретном имени файла |
| `git commit`, `git push`, создание и правка PR, комментарии | хук `publish-guard` | проверка текста публикации и `scripts/check.sh` |
| Любой прогон проверок | `scripts/guard.sh` | адреса, UUID, ключи, токены, запретные файлы в ветке, индексе и рабочем дереве |
| Чтение агентом | запреты в `.claude/settings.json` | `.env`, `*.pem`, `*.key` не читаются |

Средства платформы (GitHub secret scanning, push protection) и gitleaks в CI согласованы
([ADR-0016](../adr/0016-ci-and-tooling.md)); своих списков разрешённых значений у gitleaks нет, пометки `gitleaks:allow` не действуют
([policy.md](policy.md) §6).

## 6. Правила для LLM-агентов

- Не просить владельца прислать секрет или вывод с сервера как есть. Нужны данные — назвать
  команду, дающую отредактированный вывод (`xm diag --export`), и что в нём искать.
- Секрет, попавший в разговор, не повторять, не сохранять в файлы и не переносить в PR; сказать
  владельцу, что значение скомпрометировано и что перевыпустить.
- Не читать файлы с секретами «чтобы проверить»; проверять поведение тестом с фиктивными данными.
- Пример нужен — брать значения из §4, не «похожие на настоящие».

## 7. Если секрет утёк

1. Считать значение скомпрометированным независимо от того, как быстро его убрали.
2. Перевыпустить: профиль — удалить и создать заново; ключи REALITY — перегенерировать и раздать
   новые ссылки.
3. Убрать из рабочего дерева; попало в историю Git — сообщить владельцу: переписывание истории
   решает он.
4. Добавить в сканер или редактор правило, которое поймало бы этот случай, и тест на него.
