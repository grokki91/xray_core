# Технологический стек

Решение — [ADR-0002](../adr/0002-go-single-binary.md). Здесь — сравнение вариантов и недостатки
выбранного.

## 1. Язык менеджера

Оценки: `++` сильная сторона, `+` приемлемо, `−` слабая сторона, `−−` препятствие. Целевая
машина — 1 vCPU, 2 ГБ RAM, чистая Ubuntu. Оценки качественные: замеров памяти и размера ещё
нет, бюджеты подтверждаются в фазах 1, 2 и 7.

| Критерий | Go | Bash | Python (только stdlib) | Rust |
|---|---|---|---|---|
| Производительность | `+` | `−` | `−` | `++` |
| Память | `+` десятки МБ на процесс | `++` | `−` заметно больше у сервера UI | `++` |
| Развёртывание на VPS | `++` один статический файл | `++` уже есть | `−` своя версия интерпретатора в каждом релизе Ubuntu | `++` один файл |
| Простота поддержки | `++` типы, один формат кода, встроенные тесты | `−−` | `+` | `−` выше порог входа |
| Безопасность | `++` память, нет оболочки, `govulncheck` | `−−` кавычки и подстановки | `+` | `++` |
| Расширяемость | `++` интерфейсы, пакеты | `−−` | `+` | `++` |
| Скорость разработки (в том числе LLM) | `++` | `+` для мелкого, `−−` для большого | `++` | `−` долгая сборка |
| Интеграция с Xray-core | `++` та же экосистема | `+` | `+` | `−` |
| Кеширование сборки и зависимостей | `++` кэш модулей и сборки | — | `+` | `+` тяжёлый кэш |

Вывод: **Go, один статический бинарник** (`CGO_ENABLED=0`).

- **Bash** — прямой опыт предшественника (`grokki91/xray`): менеджер вырос до одного файла в
  7 тыс. строк, который нельзя разбить на модули с интерфейсами и покрыть тестами без живого
  сервера. Остаётся только для загрузчика `install.sh` — десятки строк.
- **Python** — версия интерпретатора зависит от релиза Ubuntu, любая внешняя библиотека тянет
  `pip` и виртуальное окружение на VPS; динамическая типизация хуже держит границы модулей.
- **Rust** — выигрыш в памяти не нужен: `xm` не работает постоянно. Плата — скорость итераций
  и отсутствие общей экосистемы с Xray и `xray_client` (оба на Go).

### Недостатки Go, которые принимаем

- Бинарник 10–15 МБ; нужен собственный конвейер релизов и цепочка доверия к нему.
- Многословность: обработка ошибок и преобразования типов дают больше строк.
- Сборщик мусора: память выше, чем у Rust, — несущественно для разовых процессов.
- Версия языка: актуальная стабильная ветка (на 2026-11 — Go 1.27, на ней собран и Xray
  v26.11.9); точная версия фиксируется в `go.mod`.

## 2. Остальные решения

| Вопрос | Выбор | Отвергнуто и почему | Недостаток выбранного |
|---|---|---|---|
| Работа с Xray | внешний бинарник и его подкоманды (`run -test`, `version`, `api statsquery`) | линковка `xray-core` как библиотеки: связывает версии, раздувает бинарник, обходит границу upstream | запуск процесса на каждую проверку; разбор текстового вывода |
| Счётчики трафика | `xray api statsquery` | собственный gRPC-клиент: тяжёлая зависимость | зависимость от формата вывода подкоманды |
| Хранение | один JSON-файл с атомарной записью | SQLite: зависимость ради десятков записей; YAML/TOML: сторонний разборщик | нет запросов и частичных обновлений — не нужны при таком объёме |
| Формат данных в репозитории | JSON | YAML: сторонняя библиотека | нет комментариев — пояснения рядом в Markdown |
| CLI | стандартный `flag` и свой диспетчер команд | cobra: зависимость ради 15 команд | автодополнение оболочки — вручную, если понадобится |
| HTTP API | `net/http` | веб-фреймворки: зависимость без выгоды | маршрутизация и проверка ввода — своим кодом |
| Web UI | статические HTML/CSS/JS без сборки, встроены через `embed` | React/Vue + сборщик: цепочка npm, сотни зависимостей; htmx: ещё одна вендорная библиотека | больше ручного кода DOM; годится только для небольшого интерфейса |
| QR-код | генерация на сервере (терминал и SVG) | библиотека в браузере | нужна реализация или небольшая Go-библиотека — решение в фазе 3 через [реестр](../dev/dependencies.md) |
| Журналы | `log/slog` → journald | собственные файлы и ротация | просмотр только через `journalctl` и `xm logs` |
| Периодические задачи | systemd-таймер и разовый процесс | постоянный демон | точность расписания — как у systemd |
| Управление службой | systemd | Docker: обязательная тяжёлая зависимость | привязка к дистрибутивам с systemd |
| Удалённый транспорт | SSH | собственный агент с открытым портом | нужен доступ по SSH с управляющей машины |
| Загрузчик | `install.sh` на Bash: скачать, сверить SHA-256, запустить `xm install` | клонирование репозитория; сборка на VPS: нужен тулчейн | доверие к `curl … | bash`; смягчение — [policy.md](../security/policy.md) §6 |
| Распространение `xm` | GitHub Releases: бинарник и `SHA256SUMS` | пакет `.deb` и свой репозиторий apt: инфраструктура | нет автообновления средствами ОС |

## 3. Чего в проекте нет и почему

- **Docker** — не обязателен и не используется: лишние сотни мегабайт и слой сети перед Xray.
- **nginx и другие фронты** — в MVP Xray слушает порт сам; REALITY сам отдаёт чужому зонду ответ
  цели. Фронт возможен позже как расширение, отдельным ADR.
- **Базы данных, очереди, брокеры** — нет задач такого масштаба.
- **Node.js на VPS и в сборке** — интерфейс не требует сборки.

## 4. Кеширование

| Что | Где | Как переиспользуется |
|---|---|---|
| Архивы релизов Xray | `/var/lib/xm/cache/` на VPS | повторная установка и откат не скачивают заново; запись кэша проверяется по SHA-256 перед использованием |
| Предыдущая версия Xray | `/usr/local/lib/xm/core/` | мгновенный откат |
| Модули и сборка Go | кэш CI | сборка и тесты не пересобирают неизменное |
| Бинарники Xray для тестов | кэш CI по версии и сумме | интеграционные тесты не скачивают их на каждый прогон |
| Инструкции LLM | неизменяемый префикс | [ai-ecosystem.md](../dev/ai-ecosystem.md) §4 |
