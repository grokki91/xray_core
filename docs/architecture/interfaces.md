# Интерфейсы

Внешние интерфейсы `xm`: команды, машинный контракт, локальный HTTP API, Web UI, мост для внешних
инструментов. Внутренние интерфейсы компонентов — [components.md](components.md).

## 1. CLI

Плоский набор коротких команд. Новая команда добавляется, только если действие нельзя выразить
флагом существующей.

| Команда | Что делает | Меняет систему |
|---|---|---|
| `xm install [--sni <домен>] [--address <адрес>] [--port <порт>]` | установка и донастройка, идемпотентно | да |
| `xm uninstall [--purge]` | убрать службу и бинарники; `--purge` — ещё состояние и снимки | да |
| `xm start` · `xm stop` · `xm restart` | управление службой Xray | да |
| `xm status` | служба, версии, адреса и порт, число профилей, дрейф, доступное обновление | нет |
| `xm update [--check] [--to <версия>] [--rollback] [--self]` | обновить Xray; `--self` — сам `xm` | да |
| `xm add [имя]` | создать профиль, показать URI и QR | да |
| `xm list` | профили: имя, дата, состояние (без секретов) | нет |
| `xm show <имя>` | URI и QR профиля повторно | нет |
| `xm rm <имя>` | удалить профиль | да |
| `xm diag [--only <категория>] [--export <файл>]` | диагностика; экспорт — отредактированный отчёт | нет |
| `xm logs [-f] [--since <время>]` | журнал Xray и `xm` | нет |
| `xm backup [--list]` | создать снимок или показать список | да |
| `xm restore <id>` | восстановить из снимка | да |
| `xm ui [--port <порт>]` | локальный Web UI для SSH-туннеля | нет |
| `xm version` · `xm help` | версии `xm` и Xray; справка | нет |

После MVP: `xm ui`, `xm install --reinstall`, перегенерация ключей, группы `xm bridge …` (§5),
`xm monitor on|off`, `xm harden` (вопрос Q7).

Общие флаги: `--json` — машинный вывод по контракту (§2); `--yes` — не задавать подтверждений.
Разрушительные действия (`uninstall --purge`, `restore`, `install --reinstall`) требуют явного
флага и подтверждения вводом слова; `--yes` заменяет только ввод, флаг обязателен.

Вывод:

- результат — stdout; ход работы и предупреждения — stderr; с `--json` в stdout ровно один документ;
- секреты печатают только команды, чьё назначение — их показать (`install`, `add`, `show`), и никогда — в журнал;
- сообщение об ошибке: что случилось, что система сделала (откат), что делать владельцу.

Коды выхода:

| Код | Смысл |
|---|---|
| 0 | успех |
| 1 | операция не удалась; если была транзакция — выполнен откат |
| 2 | неверные аргументы |
| 3 | предусловия не выполнены: ОС, права, чужая установка, занятый порт |
| 4 | `xm diag`: найдены проблемы |
| 5 | откат не удался — нужно вмешательство; текст содержит точные шаги |

## 2. Машинный контракт

Все машинные выводы (CLI `--json`, HTTP API, мост) — одни и те же типы из пакета `contract` в
общем конверте:

```json
{
  "schema": {"name": "status", "major": 1, "minor": 0},
  "xm": {"version": "0.1.0"},
  "time": 1767225600,
  "data": {}
}
```

Ошибка — тот же конверт с `schema.name = "error"` и полем `error: {code, message, hint}`;
`code` — стабильная строка вида `preflight.foreign_install`.

Правила:

- Добавление поля — `minor + 1`; потребитель обязан игнорировать неизвестные поля.
- Удаление, переименование, смена смысла — `major + 1` и запись в ADR.
- У каждой схемы — эталонный JSON в тестах; расхождение вывода с эталоном — провал.
- Потребитель с меньшим `major` получает понятную ошибку «обновите потребителя», с большим —
  «обновите `xm`». Форма конверта совпадает с принятой в `xray_client` (`schema: {name, major, minor}`).

Схемы первой версии: `status`, `profiles`, `profile`, `update`, `diag-report`, `backups`,
`version`, `error`. Формат отчёта диагностики — [diagnostics.md](../operations/diagnostics.md) §3.

## 3. Локальный HTTP API

Нужен только Web UI. Слушает `127.0.0.1`, живёт, пока запущен `xm ui`.

| Метод и путь | Назначение |
|---|---|
| `POST /api/v1/session` | обменять разовый токен на сессию |
| `GET /api/v1/status` | состояние сервера и Xray, сетевые параметры |
| `GET /api/v1/profiles` · `POST /api/v1/profiles` | список; создание |
| `GET /api/v1/profiles/{name}` | URI и QR (SVG) |
| `DELETE /api/v1/profiles/{name}` | удаление |
| `POST /api/v1/diag/runs` · `GET /api/v1/diag/runs/{id}` · `GET /api/v1/diag/runs` | запуск, результат, история |
| `GET /api/v1/update` · `POST /api/v1/update` | доступное обновление; запуск обновления |
| `GET /api/v1/jobs/{id}` | ход длительной операции |

Защита ([policy.md](../security/policy.md) §4):

- `xm ui` печатает ссылку с разовым токеном во фрагменте URL (`#…` не уходит на сервер и в
  журналы); страница меняет его на сессионную cookie `HttpOnly; SameSite=Strict`.
- Проверяются `Host` (только `127.0.0.1:<порт>` и `localhost:<порт>`) и `Origin`; изменяющие
  запросы требуют собственный заголовок.
- Ответы — `Cache-Control: no-store`; политика содержимого — только собственные ресурсы.
- Нет эндпоинтов с произвольными командами, путями файлов и управлением службой.
- Процесс завершается после 30 минут без запросов.
- Конфигурация Xray запрещает адреса назначения из частных и петлевых сетей: клиент VPN не
  может дотянуться до панели через тоннель.

## 4. Web UI

Статические HTML, CSS и JavaScript без фреймворка и без шага сборки, встроены в бинарник.

- Экраны: состояние (сервер, Xray, сеть), профили (создать, список, удалить, копировать URI,
  QR), диагностика (запуск, результаты, история), обновления.
- QR приходит с сервера готовым SVG; внешних ресурсов (шрифты, CDN, аналитика) нет.
- Данные в страницу — только через `textContent`: строки журналов и имена недоверенные.
- Доступ с ПК: `ssh -L 8088:127.0.0.1:8088 <сервер>` и `sudo xm ui` на сервере; точные команды —
  в пользовательской документации (появляется вместе с Web UI).

## 5. Мост и удалённое управление

Один принцип для внешних инструментов, внешних диагностических узлов и будущего управления
несколькими VPS: **транспорт — SSH, формат — контракт из §2, новых открытых портов нет**.

| Потребитель | Как вызывает | Что получает |
|---|---|---|
| Управляющий узел (несколько VPS, позже) | `ssh <алиас> sudo xm <команда> --json` | тот же контракт, что локально |
| Внешний диагностический узел (позже) | запускается у себя, отдаёт наблюдения | `diag-report` с `vantage.kind = "probe"` |
| `xray_client` (позже) | `ssh <алиас> sudo -n xm bridge <команда>` | факты сервера и наблюдения без секретов |

Требования к `bridge`:

- только чтение; набор команд закрытый; `sudo` без пароля разрешается правилом только на `xm bridge *`;
- в выводе нет секретов и адресов; сверка параметров профиля — по HMAC на соли сеанса, которую
  потребитель передаёт через stdin: совпадение проверяется без передачи значений;
- вывод проходит `redact`; версия контракта проверяется потребителем до разбора.

### Будущая интеграция с `xray_client`

`xray_client` (xdiag) сегодня работает с предшественником этого проекта, `grokki91/xray`: вызывает
`xm bridge facts`, `xm bridge doctor`, `xm bridge health` и разбирает контракты `bridge-facts`
(major 1), `doctor` и `health` (major 0–1). Его модель уже совпадает с принципами выше: SSH,
только чтение, соль через stdin, поле `schema`.

На текущем этапе определяется только интерфейс: пакет `bridge` над `app`, контракт из §2,
наблюдения в формате `diag-report`. Что из существующих контрактов реализуется как есть, а что
заменяется новым с адаптером на стороне `xray_client`, решается отдельным ADR после анализа его
потребностей (вопрос Q4, после MVP). До этого решения имена `bridge-facts`, `doctor`, `health`
зарезервированы и другим смыслом не занимаются.
