# Интерфейсы

Внешние интерфейсы `xm`: команды, машинный контракт, локальный HTTP API, Web UI, мост для внешних
инструментов. Внутренние интерфейсы компонентов — [components.md](components.md).

## 1. CLI

Плоский набор коротких команд. Новая команда добавляется, только если действие нельзя выразить
флагом существующей.

| Команда | Что делает | Меняет систему |
|---|---|---|
| `xm install [--sni <домен>] [--address <адрес>] [--port <порт>]` | установка на чистую машину; завершается ссылкой и QR первого профиля `profile-1`. Флаги необязательны: цель REALITY — из закрытого списка ([ADR-0035](../adr/0035-reality-target-candidates.md)), адреса — по сетевым фактам, порт — 443. Повторный запуск на своей установке — код 0, «ничего не изменено», те же ссылки; флаг, расходящийся с установленным, — код 2 | да |
| `xm uninstall [--purge [--yes]]` | убрать службу, юнит, правило UFW `xm` и бинарники; `--purge` — ещё состояние, снимки и пользователя `xray`, после ввода слова `purge` ([ADR-0042](../adr/0042-uninstall-ordered-idempotent.md)); не подтверждено — код 2, ничего не удалено; чужой юнит — код 3 | да |
| `xm start` · `xm stop` · `xm restart` | управление службой Xray | да |
| `xm status` | служба, версии, адреса и порт, дрейф, число профилей; доступное обновление — по итогу последней `xm update [--check]`, без сети ([ADR-0043](../adr/0043-verified-range-and-update-check.md)) | нет |
| `xm update [--check] [--to <версия>] [--rollback] [--self]` | обновить Xray до последней стабильной версии внутри проверенного диапазона с контролем и автоматическим откатом (провал — код 1, служба на прежней версии); `--check` — только проверить; `--to <N.N.N>` — любую стабильную, вне диапазона — с предупреждением; удержание `core.hold` — ничего не меняет, код 0 ([ADR-0043](../adr/0043-verified-range-and-update-check.md)). `--rollback` и `--self` — шаги 2 и 3 фазы 5 | да |
| `xm add [имя] [--client <id>] [--address <адрес>]` | создать профиль (без имени — `profile-N`), показать ссылку на каждый адрес сервера и QR одного из них | да |
| `xm list` | профили: имя, дата, состояние (без секретов) | нет |
| `xm show <имя> [--client <id>] [--address <адрес>]` | ссылки и QR профиля повторно | нет |
| `xm rm <имя>` | удалить профиль | да |
| `xm diag [--only <категория>] [--export <файл>]` | диагностика; экспорт — отредактированный отчёт | нет |
| `xm logs [-f] [--since <время>]` | журнал Xray и `xm` строками «время UTC источник: сообщение», отредактированный, без управляющих символов; без `--since` — последние 200 записей; `--since` — `N` m\|h\|d (1–9999) или `ГГГГ-ММ-ДД` (UTC), иначе код 2; `-f` — следить до Ctrl-C (не дольше 24 ч) ([ADR-0044](../adr/0044-journal-read-via-journalctl-stream.md)) | нет |
| `xm backup [--list]` | создать ручной снимок (хранятся 20 последних, автоснимки их не вытесняют) или показать снимки с видом, версиями и пометкой повреждённых; нужна установка | да |
| `xm restore <id> [--yes]` | восстановить состояние из снимка транзакцией: конфигурация перерисовывается, служба проверяется, текущее состояние — в автоснимке `restore`; версия Xray не меняется. Подтверждение — ввод слова `restore`; повреждённый снимок, снимок без состояния или с другим портом — код 1, ничего не изменено; работает и при повреждённом текущем состоянии | да |
| `xm ui [--port <порт>]` | локальный Web UI для SSH-туннеля | нет |
| `xm version` · `xm help` | версия `xm`; справка (версия Xray в `version` — отдельной правкой, сейчас её показывает `status`) | нет |

После MVP: `xm ui`, `xm install --reinstall`, перегенерация ключей, группы `xm bridge …` (§5),
`xm monitor on|off`, `xm harden` ([ADR-0036](../adr/0036-install-changes-only-own.md)).

`add` и `show`: ссылка на каждый заданный адрес сервера (порядок: домен, IPv4, IPv6) и QR одного — первого или названного `--address`. Флаги можно ставить до, между и после имени. Без `--client` ссылка выдаётся всегда, а клиенты, которым она не подойдёт (Hiddify 4.x, sing-box), названы в stderr с причиной из таблицы совместимости. С `--client <id>` (`v2rayn`, `v2rayng`, `hiddify-5`, `hiddify-4`, `sing-box`) несовместимый клиент — отказ с кодом 1, `profile.incompatible` и причиной; `add` при отказе профиль не создаёт; неизвестный клиент — код 2. QR несёт ANSI-цвета и предназначен терминалу: в файл и журнал его не пишут.

Команды `install`, `start`, `stop`, `restart`, `status`, `update`, `backup`, `restore` и `logs` требуют root (код 3 `preflight.not_root`).
`start`, `stop`, `restart` — не транзакции: служба, остановленная `xm stop`, остаётся остановленной после
любого изменения ([ADR-0025](../adr/0025-stopped-service-and-install-scenario.md)).

Без команды — справка в stderr и код 2; `xm help` и `xm <команда> -h` — справка в stdout, код 0.

Окружение: необязательная `XM_GITHUB_TOKEN` — токен API GitHub для `install` и `update`, если
общий внешний адрес исчерпал лимит запросов без авторизации (ответ 403); значение не по формату
(40–4096 символов `[A-Za-z0-9._-]`) — код 1 ([ADR-0031](../adr/0031-github-api-token.md)).

Общие флаги: `--json` — машинный вывод по контракту (§2); `--yes` — не задавать подтверждений.
Разрушительные действия (`uninstall --purge`, `restore`, `install --reinstall`) требуют явного
флага и подтверждения вводом слова; `--yes` заменяет только ввод, флаг обязателен.

Вывод:

- результат — stdout; ход работы и предупреждения — stderr; с `--json` в stdout ровно один документ;
- секреты печатают только команды, чьё назначение — их показать (`install`, `add`, `show`), и никогда — в журнал;
- сообщение об ошибке: что случилось, что система сделала (откат), что делать владельцу.

Коды выхода:

| Код | Смысл |
|---|---|
| 0 | успех |
| 1 | операция не удалась; если была транзакция — выполнен откат |
| 2 | неверные аргументы |
| 3 | предусловия не выполнены: ОС, права, чужая установка, занятый порт, нет установки; «уже установлено» — только гонка двух установок под блокировкой (повторный `xm install` — код 0) |
| 4 | `xm diag`: найдены проблемы |
| 5 | откат не удался — нужно вмешательство; текст содержит точные шаги |

## 2. Машинный контракт

Все машинные выводы (CLI `--json`, HTTP API, мост) — одни и те же типы из пакета `contract` в
общем конверте:

```json
{
  "schema": {"name": "status", "major": 1, "minor": 0},
  "xm": {"version": "0.1.0"},
  "time": 1767225600,
  "data": {}
}
```

Ошибка — тот же конверт с `schema.name = "error"` и полем `error: {code, message, hint}`;
`code` — стабильная строка вида `preflight.foreign_install`.

Правила:

- Добавление поля — `minor + 1`; потребитель обязан игнорировать неизвестные поля.
- Удаление, переименование, смена смысла — `major + 1` и запись в ADR.
- У каждой схемы — эталонный JSON в тестах; расхождение вывода с эталоном — провал.
- Потребитель с меньшим `major` получает понятную ошибку «обновите потребителя», с большим —
  «обновите `xm`». Форма конверта совпадает с принятой в `xray_client` (`schema: {name, major, minor}`).

Схемы первой версии: `status`, `profiles`, `profile`, `update`, `diag-report`, `backups`,
`version`, `error`. Реализованы `version` (`data: {xm}`), `status`, `update`, `backups` и
`error`; эталоны — `internal/contract/testdata/`. `status`: `installed`, `service`
(`loaded`, `active`, `sub`, `enabled`, `restarts`), `versions` (`xm`, `xray`), `addresses`
(`ipv4`, `ipv6`, `domain`), `port`, `drift`; не установлено — `installed: false`. Добавлены (`minor 1`): `profiles` —
число профилей и `clients` — таблица совместимости клиентов с пресетом и ядром сервера (`name`,
`works`, `condition`, `reason`; пусто — `[]`). Добавлено (`minor 2`): `health` — вердикт набора `control`
(`verdict`: `ok`, `degraded`, `down`, `unknown`; `cause`, `action`; `unchecked` — при `ok`, что не проверено;
не установлено — `verdict` пуст). `xm install` и `xm status` заканчиваются строкой вердикта.
Добавлено (`minor 3`): `update` — доступное обновление по итогу последней проверки (`version` — новее активной, пусто — нет; `checked` — RFC 3339, пусто — проверки не было). Схема `update` — `current`, `target`, `latest` (пусто при `--to`), `range` (`min`, `max`), `in_range`, `held`, `updated`, `checked`, `unchecked` — чего контроль не доказывает. Схема `backups` — `backups[]` от старого к новому из `id`, `created` (секунды Unix), `kind` (`auto`, `manual`), `xm`, `xray` (из манифеста; пусты у повреждённого), `valid`; `xm backup --json` — тот же документ с одним созданным снимком. Схема `profiles` — `profiles[]` из `name`, `created`
(секунды Unix), `enabled`, без секретов. Схема `profile` — те же поля и `links[]` (`address`, `uri` —
секрет), `qr_address`, `unfit[]` (`client`, `reason`); QR в документ не входит.

Ошибка аргументов при `--json` среди аргументов — документ `error` в stdout (человеку — ещё и
текст в stderr), код 2; коды `cli.unknown_command` и `cli.bad_arguments`. Команда без
машинного вывода (`help`) с `--json` — ошибка `cli.bad_arguments`. Формат отчёта диагностики — [diagnostics.md](../operations/diagnostics.md) §3.

## 3. Локальный HTTP API

Нужен только Web UI. Слушает `127.0.0.1`, живёт, пока запущен `xm ui`.

| Метод и путь | Назначение |
|---|---|
| `POST /api/v1/session` | обменять разовый токен на сессию |
| `GET /api/v1/status` | состояние сервера и Xray, сетевые параметры |
| `GET /api/v1/profiles` · `POST /api/v1/profiles` | список; создание |
| `GET /api/v1/profiles/{name}` | URI и QR (SVG) |
| `DELETE /api/v1/profiles/{name}` | удаление |
| `POST /api/v1/diag/runs` · `GET /api/v1/diag/runs/{id}` · `GET /api/v1/diag/runs` | запуск, результат, история |
| `GET /api/v1/update` · `POST /api/v1/update` | доступное обновление; запуск обновления |
| `GET /api/v1/jobs/{id}` | ход длительной операции |

Защита ([policy.md](../security/policy.md) §4):

- `xm ui` печатает ссылку с разовым токеном во фрагменте URL (`#…` не уходит на сервер и в
  журналы); страница меняет его на сессионную cookie `HttpOnly; SameSite=Strict`.
- Проверяются `Host` (только `127.0.0.1:<порт>` и `localhost:<порт>`) и `Origin`; изменяющие
  запросы требуют собственный заголовок.
- Ответы — `Cache-Control: no-store`; политика содержимого — только собственные ресурсы.
- Нет эндпоинтов с произвольными командами, путями файлов и управлением службой.
- Процесс завершается после 30 минут без запросов.
- Конфигурация Xray запрещает адреса назначения из частных и петлевых сетей: клиент VPN не
  может дотянуться до панели через тоннель.

## 4. Web UI

Статические HTML, CSS и JavaScript без фреймворка и без шага сборки, встроены в бинарник.

- Экраны: состояние (сервер, Xray, сеть), профили (создать, список, удалить, копировать URI,
  QR), диагностика (запуск, результаты, история), обновления.
- QR приходит с сервера готовым SVG; внешних ресурсов (шрифты, CDN, аналитика) нет.
- Данные в страницу — только через `textContent`: строки журналов и имена недоверенные.
- Доступ с ПК: `ssh -L 8088:127.0.0.1:8088 <сервер>` и `sudo xm ui` на сервере; точные команды —
  в пользовательской документации (появляется вместе с Web UI).

## 5. Мост и удалённое управление

Один принцип для внешних инструментов, внешних диагностических узлов и будущего управления
несколькими VPS: **транспорт — SSH, формат — контракт из §2, новых открытых портов нет**.

| Потребитель | Как вызывает | Что получает |
|---|---|---|
| Управляющий узел (несколько VPS, позже) | `ssh <алиас> sudo xm <команда> --json` | тот же контракт, что локально |
| Внешний диагностический узел (позже) | запускается у себя, отдаёт наблюдения | `diag-report` с `vantage.kind = "probe"` |
| `xray_client` (позже) | `ssh <алиас> sudo -n xm bridge <команда>` | факты сервера и наблюдения без секретов |

Требования к `bridge`:

- только чтение; набор команд закрытый; `sudo` без пароля разрешается правилом только на `xm bridge *`;
- в выводе нет секретов и адресов; сверка параметров профиля — по HMAC на соли сеанса, которую
  потребитель передаёт через stdin: совпадение проверяется без передачи значений;
- вывод проходит `redact`; версия контракта проверяется потребителем до разбора.

### Будущая интеграция с `xray_client`

`xray_client` (xdiag) сегодня работает с предшественником этого проекта, `grokki91/xray`: вызывает
`xm bridge facts`, `xm bridge doctor`, `xm bridge health` и разбирает контракты `bridge-facts`
(major 1), `doctor` и `health` (major 0–1). Его модель уже совпадает с принципами выше: SSH,
только чтение, соль через stdin, поле `schema`.

На текущем этапе определяется только интерфейс: пакет `bridge` над `app`, контракт из §2,
наблюдения в формате `diag-report`. Что из существующих контрактов реализуется как есть, а что
заменяется новым с адаптером на стороне `xray_client`, решается отдельным ADR после анализа его
потребностей (вопрос Q4, после MVP). До этого решения имена `bridge-facts`, `doctor`, `health`
зарезервированы и другим смыслом не занимаются.
