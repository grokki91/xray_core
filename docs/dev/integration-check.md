# Проверка на реальной интеграции

Как агент решает, что изменение должен проверить владелец на своей машине, какой скрипт ему
выдаёт и как по присланной строке выносит вердикт «Готово к Pull Request». Решение —
[ADR-0021](../adr/0021-owner-integration-check.md); исполнитель — субагент `integration-check`
(`.claude/agents/integration-check.md`).

Разделы: [когда](#1-когда-нужна) · [где](#2-где) · [требования к скрипту](#3-требования-к-скрипту) ·
[как выдать](#4-как-выдать-владельцу) · [вердикт](#5-вердикт).

## 1. Когда нужна

По умолчанию — не нужна, и в ответе об этом ничего не пишется. Нужна, только если заявленный
эффект изменения не доказывают уровни L0–L4 ([testing.md](../testing.md) §2) в CI и в сессии.

| Нужна | Не нужна |
|---|---|
| поведение в настоящей сети VPS: публичный IPv4 и IPv6, фаервол хостера, DNS, MTU | документы, инструкции, хуки, CI |
| настоящие клиенты на Windows 11: импорт ссылки и QR, подключение | логика, покрытая L1–L2 |
| ОС и версия VPS владельца, которых нет в матрице L4 | поведение Xray, покрытое L3 |
| загрузчик `install.sh` с настоящего адреса выпуска | установка, юнит, права, если их покрывает L4 в CI |
| сам каркас скриптов этого документа на настоящей ОС | — |

## 2. Где

| Место | Когда | Каркас |
|---|---|---|
| VPS — Ubuntu, bash | эффект на стороне сервера | `scripts/integration/vps.sh` |
| Windows 11 — Windows PowerShell 5.1 | эффект на стороне клиента | `scripts/integration/win11.ps1` |

Одна проверка — одно место. Нужны оба — две проверки, у каждой свой идентификатор и строка.

## 3. Требования к скрипту

Каркас уже выполняет общие требования; агент меняет только параметры (идентификатор, полный
SHA головы PR, нужен ли root или администратор, инструменты) и тело шагов.

| Требование | Как |
|---|---|
| Один самодостаточный файл | сам создаёт песочницу, ставит недостающее, скачивает коммит по SHA с `github.com` и сверяет его |
| Права | VPS: `sudo` только при `NEED_ROOT=1` или установке пакетов, пароль спрашивается до тихих шагов. Windows: при `$NeedAdmin` без прав администратора — `FAIL admin`; установщик winget может спросить UAC |
| Инструменты | только пакетный менеджер ОС (`apt-get`, `winget`) и адреса из [dependencies.md](dependencies.md); иное — согласие владельца и строка в реестре |
| Песочница | всё — во временном каталоге: исходники, журнал, `TMPDIR`/`TEMP`, кэши Go; удаляется в конце при любом исходе |
| Уборка | удаляются только пакеты, поставленные скриптом (VPS — разница списков `dpkg` до и после) |
| Рабочая установка | `xm`, Xray, состояние, юниты, фаервол не меняются; новых публичных портов нет, слушать — только `127.0.0.1`. Проверке нужна смена живой системы — это не скрипт, а вопрос владельцу о разрушительной операции |
| Вывод | вывод шагов — в журнал песочницы; в консоль — одна строка §5. В ней только открытые данные (S3, [secrets.md](../security/secrets.md) §1) |
| Шаги | одно проверяемое утверждение на шаг с говорящим именем: имя — единственное, что агент узнает о провале |
| Перед выдачей | VPS: `bash -n` и `shellcheck`; каркас покрыт `tests/test-integration-skeleton.sh`. Windows: разбора PowerShell в сессии нет — каркас проверяется на Windows 11 владельцем |

## 4. Как выдать владельцу

Один блок, который вставляется в терминал целиком; скрипт сохраняется во временный файл, чтобы
команды внутри не читали его со стандартного ввода, и файл удаляется после запуска.

VPS — терминал под обычным пользователем с `sudo` или под root:

```bash
f=$(mktemp) && cat >"$f" <<'XM_CHECK_EOF'
…заполненный scripts/integration/vps.sh…
XM_CHECK_EOF
bash "$f"; rm -f "$f"
```

Windows 11 — PowerShell; «от имени администратора» — только если в скрипте `$NeedAdmin = $true`:

```powershell
$f = Join-Path $env:TEMP 'xm-check.ps1'
@'
…заполненный scripts/integration/win11.ps1…
'@ | Set-Content -LiteralPath $f -Encoding UTF8
powershell -NoProfile -ExecutionPolicy Bypass -File $f; Remove-Item -LiteralPath $f
```

`-ExecutionPolicy Bypass` действует только на этот запуск и не меняет политику системы.

## 5. Вердикт

Строка результата: `XM-CHECK <id> <sha7> PASS|FAIL <шаг> clean|dirty`. Ожидаемая —
`XM-CHECK <id> <sha7> PASS clean`.

| Прислано | `Готово к Pull Request` |
|---|---|
| строка совпала с ожидаемой, `sha7` — текущая голова PR | `True` |
| `FAIL <шаг>` | `False` — что означает провал этого шага; исправление в PR или новый скрипт с более мелкими шагами |
| `dirty` | `False` — что могло остаться и команда уборки |
| другой `sha7` или `id` | `False` — проверен не тот коммит или не тот скрипт |
| что-то кроме одной строки | `False` — сырой вывод не разбирается и не цитируется ([secrets.md](../security/secrets.md) §6) |

Поле `Готово к Pull Request` появляется в ответе только после присланной строки. Новый коммит в
PR после `True` отменяет вердикт: проверка повторяется на новой голове. Новый скрипт получает
новый `id` (суффикс `-2`, `-3`). Слияние — по-прежнему решение владельца
([ADR-0018](../adr/0018-short-pr-and-draft-only.md)).
