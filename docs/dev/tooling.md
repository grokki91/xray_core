## 2. Предлагается подключить

### GitHub Actions: обязательные проверки

1. **Назначение**: запускать `scripts/check.sh` (позже — сборку, тесты L1–L4, выпуск) на каждый
   PR независимо от того, чем и кем сделан коммит.
2. **Преимущества**: хуки Claude Code защищают только сессии Claude Code; CI — единственная
   гарантия для людей и других инструментов. Размещённые исполнители с Ubuntu 22.04 и 24.04 —
   готовые чистые машины с systemd для системных тестов.
3. **Недостатки**: зависимость от платформы; системные тесты удлиняют проверку PR на минуты.
4. **Безопасность**: чужой код в конвейере — действия (`actions/checkout` и др.). Смягчение:
   фиксация по хэшу коммита, права `contents: read`, без секретов в заданиях проверок.
5. **Сложность**: один файл на десяток строк сейчас; растёт вместе с тестами.

### Secret scanning и push protection GitHub

1. **Назначение**: платформа сама отклоняет отправку с распознанными токенами и сообщает о
   найденных в истории.
2. **Преимущества**: бесплатно для публичных репозиториев; срабатывает даже при обходе
   локальных проверок.
3. **Недостатки**: знает форматы токенов известных сервисов; ключи REALITY, UUID и адреса не
   распознаёт — их ловит `scripts/guard.sh`.
4. **Безопасность**: только улучшает; данные уже у GitHub.
5. **Сложность**: два переключателя в настройках репозитория; кода нет.

### gitleaks

1. **Назначение**: сканер секретов по правилам и энтропии: рабочее дерево и история.
2. **Преимущества**: сотни готовых правил, проверка всей истории, один бинарник.
3. **Недостатки**: ложные срабатывания на тестовых данных требуют настройки; дублирует часть
   `scripts/guard.sh`. Свой сканер остаётся: правила про данные установки (адреса, UUID, ключи
   REALITY) специфичны для проекта.
4. **Безопасность**: сторонний бинарник в CI — фиксировать версию и сумму; ничего не отправляет наружу.
5. **Сложность**: файл настройки и шаг CI.

### govulncheck

1. **Назначение**: официальный сканер уязвимостей Go: сообщает только о тех, чей код реально
   вызывается.
2. **Преимущества**: мало шума; поддерживается командой Go; проверяет и стандартную библиотеку.
3. **Недостатки**: нужен доступ к базе уязвимостей во время проверки.
4. **Безопасность**: улучшает; инструмент из экосистемы Go.
5. **Сложность**: один шаг CI.

### staticcheck

1. **Назначение**: статический анализ Go сверх `go vet`: ошибки, мёртвый код, устаревшие вызовы.
2. **Преимущества**: высокая точность, почти без настройки.
3. **Недостатки**: ещё один инструмент с собственной версией.
4. **Безопасность**: сторонний модуль только в CI и у разработчика, в бинарник не попадает.
5. **Сложность**: один шаг CI.

### shellcheck

1. **Назначение**: анализ Bash: `install.sh`, хуки, `scripts/`.
2. **Преимущества**: ловит ошибки кавычек и подстановок — главный класс уязвимостей оболочки;
   загрузчик исполняется от root.
3. **Недостатки**: часть замечаний стилистические, нужны точечные отключения с причиной.
4. **Безопасность**: улучшает; инструмент в поставку не входит.
5. **Сложность**: один шаг CI; пакет в стандартных репозиториях Ubuntu.

### Dependabot

1. **Назначение**: предложения обновить действия CI и модули Go.
2. **Преимущества**: встроен в GitHub; фиксация действий по хэшу без него быстро устаревает.
3. **Недостатки**: шум PR; каждое обновление всё равно проходит правило реестра.
4. **Безопасность**: улучшает актуальность; обновления не сливаются автоматически.
5. **Сложность**: один файл настройки.

### Подтверждение происхождения сборки (artifact attestations)

1. **Назначение**: подписанное свидетельство, что бинарник `xm` собран конвейером этого
   репозитория из конкретного коммита.
2. **Преимущества**: закрывает вопрос «откуда этот файл» сильнее, чем `SHA256SUMS`, лежащий
   рядом с бинарником; встроено в GitHub.
3. **Недостатки**: проверка требует `gh` на стороне проверяющего; `install.sh` на чистом VPS
   проверяет только сумму.
4. **Безопасность**: улучшает; новых секретов не требует.
5. **Сложность**: один шаг в конвейере выпуска.

## 4. Системы спецификаций

### OpenSpec

Состояние на 2026-11-13: версия 2.0.0, лицензия MIT; ставится отдельным CLI либо через npm
(нужен Node.js ≥ 22.12).

1. **Назначение**: процесс «предложение → реализация → архив»: команды агента создают в
   `openspec/changes/<имя>/` файлы `proposal.md`, `design.md`, `tasks.md` и изменения
   требований, а после реализации переносят их в постоянные спецификации `openspec/specs/`.
2. **Преимущества**: требования записаны сценариями «когда — тогда» и переживают сессию;
   изменения описываются дельтами — удобно для существующего кода; работает с разными
   агентами; план проверяется до написания кода.
3. **Недостатки**: второе дерево документов рядом с `docs/` — требования и архитектура
   начнут жить в двух местах и расходиться; собственные команды и форматы поверх наших скилов
   и брифа; каждая мелкая задача обрастает четырьмя файлами.
4. **Безопасность**: на VPS не попадает; на машине разработчика — CLI и, при установке через
   npm, цепочка зависимостей Node.js. В файлы предложений действуют те же правила о секретах.
5. **Сложность**: заметная: новый процесс, который нужно соблюдать во всех сессиях.

Предложение: **сейчас не подключать**. То, что OpenSpec даёт на старте, уже закрыто без
зависимостей: решения — ADR, границы — `components.md`, задачи — фазы и бриф. Его сильная
сторона — дельты требований в живом коде при нескольких параллельных изменениях — понадобится не
раньше, чем появится код и поток изменений. Пересмотреть после MVP; при подключении
`openspec/specs/` должен заменить соответствующие разделы `docs/`, а не дублировать их.

### GitHub Spec Kit и аналоги

Тот же класс: спецификация → план → задачи → реализация, со своими командами и шаблонами.
Состояние не перепроверялось. Оценка совпадает с OpenSpec: дублирование `docs/`, новый процесс;
преимуществ перед OpenSpec для этого проекта не видно. Не подключать.

## 5. Не подключать

| Инструмент | Почему нет |
|---|---|
| golangci-lint | агрегатор десятков линтеров с большой настройкой; `go vet` и staticcheck закрывают нужное |
| GoReleaser | выпуск — `go build` и `sha256sum` в несколько строк; инструмент оправдан при пакетах и многих платформах |
| cosign | подтверждение происхождения сборки решает ту же задачу без отдельного инструмента и ключей |
| trivy, osv-scanner | контейнеров нет; для Go точнее govulncheck |
| pre-commit (фреймворк) | зависимость от Python и сети; обязательные проверки уже собраны в `scripts/check.sh` |
| go-arch-lint, depguard | границы проверяет собственный тест графа импортов на стандартной библиотеке |
| Фреймворки агентных процессов (наборы ролей и команд поверх агента) | дублируют `AGENTS.md`, скилы и субагентов; расходуют контекст |
| Дополнительные MCP-серверы | для разработки не нужны; каждый — новая поверхность для внедрения инструкций |
| Автоматическое ревью PR агентом в CI | рассмотреть после MVP: требует ключа API в секретах репозитория и бюджета |
