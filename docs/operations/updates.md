# Обновление Xray-core

Решение — [ADR-0009](../adr/0009-update-source-and-verification.md). Цель: обновление одной
командой, которое либо завершается работающей службой на новой версии, либо возвращает прежнюю.

## 1. Источник

- Единственный источник — релизы `XTLS/Xray-core` на GitHub. Адреса, с которых разрешена
  загрузка, — закрытый список в коде (`api.github.com`, `github.com` и узел раздачи файлов
  релизов GitHub); только HTTPS; перенаправление на адрес вне списка — ошибка.
- Зеркала, сторонние сборки и установочный скрипт `XTLS/Xray-install` не используются: скрипт
  сверяет только SHA-256, не умеет откат и сам исполнялся бы без проверки.
- Файл релиза для целевой машины — `Xray-linux-64.zip` и `Xray-linux-64.zip.dgst`.

## 2. Версии

| Понятие | Смысл |
|---|---|
| Канал | стабильные релизы; предварительные (`pre-release`) не предлагаются |
| Проверенный диапазон | версии Xray, на которых прошли тесты данной версии `xm`; хранится в `xm` данными |
| Удержание | `core.hold = true`: `xm update` ничего не делает, пока владелец не снимет |
| Предыдущая версия | остаётся на диске для отката |

- `xm update` ставит последнюю стабильную версию **внутри проверенного диапазона**.
- `xm update --to <версия>` ставит любую; вне диапазона — с предупреждением, что именно не
  проверено.
- Диапазон расширяется выпуском `xm`: новая версия Xray прогоняется через интеграционные тесты
  ([testing.md](../testing.md) L3) и таблицу совместимости клиентов
  ([compatibility.md](../compatibility.md)). Причина: обновление сервера может молча отрезать
  клиентов — так произошло с правилом X25519MLKEM768 в v26.9.9.
- Автоматического обновления по расписанию в MVP нет (вопрос Q9): `xm status` показывает, что
  доступна новая версия.

## 3. Проверка целостности

Проверено на релизе v26.11.9 (2026-11-13): upstream публикует рядом с архивом файл `.dgst` со
строками `MD5=`, `SHA1=`, `SHA2-256=`, `SHA2-512=`; подписей и подтверждений происхождения
сборки нет.

Порядок:

1. Скачать `.dgst` и архив во временный каталог кэша; размер ограничен.
2. Сверить **SHA2-256 и SHA2-512** архива со значениями из `.dgst`; MD5 и SHA1 не используются.
3. Если API GitHub отдаёт собственный хэш файла релиза — сверить и с ним (наличие поля
   подтвердить в фазе 2).
4. Распаковать с защитой от выхода путей из каталога; взять только `xray`.
5. Убедиться, что это ELF под архитектуру машины и что `xray version` называет ожидаемую версию.
6. Архив из кэша перед повторным использованием проходит шаг 2 заново.

Ограничение: суммы лежат там же, где архив. Проверка ловит порчу при доставке и в кэше, но не
подмену релиза у самого upstream ([policy.md](../security/policy.md), T8).

## 4. Порядок обновления

Транзакция `app` ([ADR-0005](../adr/0005-transactions-and-rollback.md)):

1. Блокировка; определить целевую версию (§2); совпадает с текущей — выход с кодом 0.
2. Загрузка и проверка (§3) в `/usr/local/lib/xm/core/<новая>/`.
3. **До переключения**: `xray run -test` новой версией на действующей конфигурации. Провал —
   служба не тронута, выход с кодом 1.
4. Снимок состояния.
5. Атомарно переключить ссылку `current`; перезапустить службу.
6. Контроль (§5).
7. Успех — записать версии в состояние, удалить версии старше предыдущей. Провал — откат (§6).

Геоданные (`geoip.dat`, `geosite.dat`) не ставятся и не обновляются: конфигурация их не
использует ([policy.md](../security/policy.md) §4).

## 5. Контроль после обновления

| Проверка | Что доказывает |
|---|---|
| служба активна и не перезапускается в цикле | бинарник стартует с этой конфигурацией |
| порт слушается на IPv4 и IPv6 | входящий поднят |
| самопроверка: клиент на том же бинарнике Xray проходит через петлю до тестового адреса | сквозной путь: рукопожатие, аутентификация, исходящий, DNS |

Чего контроль не доказывает: что сторонние клиентские ядра (sing-box и его форки) по-прежнему
подключаются. Это закрывают только проверенный диапазон и таблица совместимости; сообщение об
успехе говорит об этом прямо.

## 6. Откат

- Автоматический — при провале шагов 5–6: вернуть `current` на предыдущую версию, перезапустить,
  повторить контроль. Команда завершается кодом 1 и сообщает причину и то, что служба работает на
  прежней версии.
- Ручной — `xm update --rollback`: та же транзакция в обратную сторону.
- Если и предыдущая версия не проходит контроль — код 5: `xm` печатает, что проверено, что не
  работает и какие команды выполнить; ничего больше не меняет.

## 7. Пользовательская конфигурация

Обновление не меняет `state.json`, профили и ключи. Конфигурация Xray перерисовывается только
если новая версия `xm` изменила пресет; это отдельная транзакция со своим снимком.

## 8. Обновление самого `xm`

После MVP; до тех пор `xm` обновляется повторным запуском `install.sh`.

`xm update --self`: релиз этого репозитория, бинарник и `SHA256SUMS`, тот же порядок — загрузка,
проверка, замена с сохранением предыдущего файла, `xm version`, миграция состояния внутри
транзакции, откат при провале.

## 9. Что остаётся вне механизма

- Обновления ОС и ядра — дело системы (аудит подсказывает, включены ли автоматические обновления).
- Обновление клиентов — дело владельца; `xm` показывает минимальные версии из таблицы совместимости.
