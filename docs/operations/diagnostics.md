# Диагностика

Решение — [ADR-0011](../adr/0011-diagnostics-evidence-model.md). Диагностика измеряет
наблюдаемое и честно говорит, чего измерить не может. Она не определяет «заблокировано ли» —
она показывает, что работает, что нет и откуда это видно.

## 1. Модель

```
проверка (Check) → наблюдения (Observation) → правила анализа → выводы (Finding) → отчёт (Report)
```

- **Наблюдение** — результат одного измерения из одной точки наблюдения: что, когда, к чему,
  значение, состояние `ok | fail | skip | error`. `skip` всегда с причиной («нет IPv6-адреса»,
  «нужна внешняя точка»).
- **Вывод** — утверждение о причине, собранное из наблюдений, с классом:

| Класс | Когда допустим | Обязательные поля |
|---|---|---|
| `fact` | прямо следует из наблюдений этой точки («служба не активна», «цель не поддерживает TLS 1.3») | ссылки на наблюдения |
| `probable` | вытекает из двух и более независимых наблюдений, но объяснимо иначе | наблюдения, альтернативные объяснения |
| `hypothesis` | объясняет картину, но из доступных точек не проверяется | что подтвердит и что опровергнет |

Правила, которые нельзя ослабить:

1. **Таймаут ≠ фильтрация.** Отсутствие ответа объясняется десятком причин; сам по себе таймаут
   даёт только наблюдение.
2. Вывод о сетевой фильтрации, DPI или ТСПУ никогда не имеет класс `fact`.
3. С одной локальной точкой он не выше `hypothesis`. Класс `probable` — только если одновременно:
   локальные проверки сервера в порядке, минимум одна внешняя точка подключается, минимум одна
   внешняя точка в том же окне времени — нет.
4. У каждого наблюдения есть `limits` — что это измерение не различает.
5. Отчёт сначала показывает факты, затем вероятные причины, затем гипотезы — раздельно.

## 2. Точки наблюдения

| Вид | Что это | Когда |
|---|---|---|
| `local` | сам сервер | MVP |
| `probe` | внешний узел: другой VPS или ПК, запускающий те же проверки доступности к серверу | после MVP |
| `client` | клиентское устройство (`xray_client`) | после MVP, через импорт наблюдений |

Все точки отдают наблюдения одного формата (§3), поэтому сравнение — задача анализа, а не
транспорта: наблюдения с одинаковым `check` и близким временем складываются в строку «точка →
результат». Различие между точками — материал для вывода `probable`; совпадение провала во всех
точках указывает на сервер, а не на путь. Сбор с внешних узлов — по SSH
([interfaces.md](../architecture/interfaces.md) §5).

## 3. Формат отчёта

Схема `diag-report`, конверт — [interfaces.md](../architecture/interfaces.md) §2. Пример поля
`data` после редактирования:

```json
{
  "id": "20260101T000000Z",
  "vantage": {"kind": "local", "id": "server"},
  "env": {"xm": "0.1.0", "xray": "26.11.9", "os": "ubuntu-24.04"},
  "observations": [
    {
      "check": "reach.listen",
      "target": "<server-ip>:443",
      "status": "ok",
      "value": {"ipv4": true, "ipv6": true},
      "limits": ["порт слушается локально; доступность извне этим не доказана"]
    }
  ],
  "findings": [
    {
      "code": "reach.external.unknown",
      "class": "hypothesis",
      "title": "Доступность порта из внешних сетей не проверена",
      "evidence": ["reach.listen"],
      "confirm": "подключение внешней точки наблюдения",
      "actions": ["проверить подключение клиентом из другой сети"]
    }
  ],
  "summary": {"ok": 21, "fail": 0, "skip": 4, "error": 0}
}
```

## 4. Каталог проверок

Идентификатор — `<категория>.<предмет>[.<свойство>]`. Каталог — данные реестра; ниже — состав
первой полной версии (фаза 6). Проверки с пометкой MVP входят в минимальный набор фазы 5.

| Категория | Проверки | Ограничения измерения |
|---|---|---|
| `xray` — состояние Xray-core | установлен и версия в проверенном диапазоне (MVP); служба активна, нет цикла перезапусков (MVP); конфигурация проходит `xray run -test` (MVP); дрейф конфигурации (MVP); ошибки в журнале по видам | журнал показывает симптомы, не причины |
| `reach` — доступность сервера | порт слушается на IPv4 и IPv6 (MVP); локальный фаервол пропускает порт (MVP); самопроверка через петлю (MVP); доступность извне | локально доказывается только «сервер готов принимать»; извне — нужна точка `probe` |
| `ipv4`, `ipv6` | адрес, маршрут по умолчанию, исходящее соединение по каждому семейству (MVP) | исходящая связность не доказывает входящую |
| `dns` | системный резолвер отвечает; DoH-серверы из конфигурации отвечают; ответы резолвера и DoH на контрольные имена совпадают; резолвинг через тоннель | расхождение ответов бывает законным (CDN) |
| `tls` | цель REALITY: достижима, TLS 1.3, h2, X25519MLKEM768, срок сертификата; расхождение часов сервера | проверяется путь от сервера до цели, не от клиента до сервера |
| `conn` — соединения, таймауты, потери | время установления TCP до контрольных узлов; доля таймаутов; доля повторных передач по счётчикам ядра за время прогона; потери ICMP, если доступен `ping` | контрольные узлы — закрытый документированный список; малая выборка |
| `route` — маршрутизация | маршруты по умолчанию; ошибки «сеть недостижима»; путь к цели REALITY | трассировка в MVP не выполняется |
| `ssh` — доступность SSH | служба активна; порт слушается; замечания аудита настроек | доступность SSH извне — только точкой `probe` |
| `change` — изменения доступности | что изменилось относительно прошлого отчёта; переходы «доступно → недоступно» из хронологии мониторинга | нужен включённый мониторинг и накопленная история |
| `filter` — признаки фильтрации | число отклонённых рукопожатий в журнале Xray; падение трафика до нуля при здоровой службе; расхождение между точками наблюдения | наблюдения — факты о журнале и счётчиках; их объяснение фильтрацией — не выше `hypothesis` без внешних точек (§1) |
| `probe` — разные внешние сети | TCP, TLS и полное рукопожатие с внешних точек | после MVP |

## 5. Ресурсы и поведение

- Прогон по умолчанию — не дольше 30 секунд и не больше 20 исходящих соединений; тяжёлые
  проверки запускаются только явным выбором (`--only`).
- Диагностика ничего не меняет в системе и не перезапускает службу.
- Проверка, которой нечем измерить, возвращает `skip` с причиной; подмены метода «на что
  получится» нет.
- К одному узлу — без серий одновременных соединений: измерение не должно само выглядеть аномалией.

## 6. История и анализ накопленного

- Каждый отчёт сохраняется отредактированным ([data-model.md](../architecture/data-model.md) §5).
- Проверки категории `change` сравнивают отчёты между собой; хронология `monitor` даёт моменты
  переходов.
- Автоматизированный анализ накопленных данных (закономерности по времени суток, сетям,
  версиям) — расширение после фазы 6: он читает те же отчёты и замеры и подчиняется тем же
  правилам классов.

## 7. Экспорт

`xm diag --export <файл>` — отчёт, прошедший редактор: без адресов, идентификаторов, ключей,
доменов установки ([secrets.md](../security/secrets.md) §3). Это единственная форма, в которой
данные диагностики можно показывать вне сервера, в том числе LLM.

## 8. Как добавить проверку

Порядок — скил `diagnostics` (`.claude/skills/diagnostics/SKILL.md`): идентификатор, наблюдение с
`limits`, правило анализа с классом, тест на каждое состояние, строка в таблице §4.
